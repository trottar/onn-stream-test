# D-BASE-P8 task handoff — the hole that comes once every two seconds

**The clue `P7` left.** The audio arrival stream has a 55-60 ms hole about **once every 2 s** (93 % of 2 s ticks carry one; the sender paces to 5.0 ms ± 0.08). Two things in this system run on a 2 s cadence: the client's **heartbeat** (an HTTP POST from the onn to the companion every 2 s) and the P5 **socket sampler** (`adb shell cat /proc/net/udp6` every 2 s, host-driven). `S2` had the holes at 75.9/min before the sampler existed, so the sampler cannot be the whole story, but the heartbeat existed then. A 50 ms stall on the onn during an HTTP round trip on a thread that shares something with the audio receive thread — a lock, a CPU core, the main looper — is the cheapest explanation on the table, and it is testable without guessing. Read first: docs/memory/evidence/D_BASE_P7_STARVATION_COUNTER_2026-09-22.md (§5-§7), D_BASE_P5_WHICH_QUEUE_2026-09-21.md (the sampler), PrivyHub/app/src/main/java/streaming/NativeAudioReceiver.kt (the receive loop and `maxArrivalGapMs`), NativeStreamActivity.kt (where and on which thread the heartbeat is built and sent), docs/memory/TOOLS.md.

Dump the ring at session end into the decoder session report under `audio.arrival_holes` (start, length, ms since last heartbeat start, in-flight flag).
