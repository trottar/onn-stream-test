# D-BASE-P6 task handoff — control the frame-size tail and watch the loss

**Where this stands (P5, 2026-09-21):** loss on the production path is upstream of the onn's socket and tracks the count of large frames (frames ≥ 80 packets, Spearman 0.78 per minute; p50 frame 11 packets, p99 ~80, max 207). The content-lock (O1) makes one 20-minute attract session per arm directly comparable. This run characterizes the most direct control of that variable first — the encoder's **maximum frame size** — then conventional rate control, with baseline bookends to catch environment drift. **Nothing here is adopted**; every arm is a knob set for one session, and the default is restored and re-measured at the end.

Read first: docs/memory/evidence/D_BASE_P5_WHICH_QUEUE_2026-09-21.md (§4, §7, §8), O1_OPAL_AIR_VIEW_2026-09-21.md (§1, §2), D_BASE_P3_SENDER_PACING_2026-09-21.md, docs/memory/TOOLS.md, companion/native_stream.py (the encoder command: `h264_vaapi`, CBR 7000 kbps, GOP 15, `-bf 0`, `pkt_size=1200`), companion/native_fec_relay.py (the P5 frame-size counters).

**Step 0 — inventory the installed control surface, and prove each knob bites before spending a session on it.** `ffmpeg -h encoder=h264_vaapi` and `vainfo` on this host: record FFmpeg version, Mesa/driver version, the RC modes offered, and whether `max_frame_size`, `-maxrate`, `-bufsize`, `rc_mode`, `slices`, and any intra-refresh option exist. Current RC mode must be stated (max_frame_size is unavailable in CQP). Then, for each knob to be tested, a **60-second smoke session** with the relay's P5 counters: if `max_frame_size` is set to N bytes and the per-frame payload bytes still exceed N routinely, the driver is ignoring it — record that as a finding and drop the arm rather than running it; likewise if `-bufsize` does not move the tail at all. Add **per-frame payload bytes** to the relay's counters alongside packets (sum of RTP payload lengths per RTP timestamp; max, p99 and count above the cap per second), so the cap is checked in the unit it is set in. Keep the packet-count columns; report the bytes-to-packets mapping observed (bytes per packet is ~1,188 payload at `pkt_size=1200`; measure it).

**Choosing the caps from measured bytes, not from 80 × 1200.** From the baseline arm's per-frame byte distribution, find the byte size at which loss begins to rise sharply (the knee — bucket the baseline's frames by size and compute loss per bucket as below). Set **A1** to a cap just below the knee and **A2** to ~25-35 % lower than A1. For the VBV arm, the one-frame budget is `bitrate / fps` = 7,000,000 / 60 ≈ 116,700 bits ≈ 14.6 KB per frame; **B1** is `-maxrate 7000k -bufsize <1x one-frame budget>` in bits (≈ 117k); if it proves too tight to run at all in the smoke test, use 2x and say so. Do **not** combine `max_frame_size` with tight VBV in any arm.

**Arms, in this order, one 20-minute attract-mode session of the PS1 reference title each, zero input, per TOOLS.md, BACK to end, teardown and companion restart between (the arm is whatever the encoder was started with — confirm the encoder command line in the session's host metadata before each stream opens):**

| arm | encoder change | establishes |
| --- | --- | --- |
| A0 | none (default) | fresh baseline |
| A1 | `max_frame_size` just below the knee | whether removing the tail removes the loss |
| A2 | `max_frame_size` ~25-35 % lower | the shape of loss vs. constraint |
| B1 | `-maxrate 7000k -bufsize` one-frame budget (VBV), no max_frame_size | whether conventional RC yields a similar tail |
| A0′ | default restored | environment drift during the run |

Confirm the default is byte-for-byte restored before A0′ (diff the encoder command against A0's).

**Per arm, record:** the per-frame size distribution (packets and bytes: p50 / p90 / p99 / max, frames ≥ 40 / ≥ 80 packets, frames above the cap), **loss conditional on frame-size bucket** (< 40, 40-59, 60-79, ≥ 80 packets: for each bucket the number of frames and the loss attributed to the 10 s windows dominated by that bucket — state the attribution method; a per-frame loss attribution is not available, so use windows), lost packets and loss per minute, forward-gap events, max forward gap, sequence resyncs, **achieved encoder bitrate** (mean and per-minute, from the encoder log's `size=`/`time=` line, plus the relay's `rtp_bytes`), rendered fps, `spike_20_ms`/min, `max_output_gap_ms`, `max_rx_to_decode_ms`, audio loss, and the per-minute loss series for the cross-arm comparison. Also the encoder's CPU % and the host's GPU power from the T1 sampler, since a tighter RC can cost encoder time.

**Reading, pre-registered.** Because the content-lock repeats the same tail every session, compare arms minute by minute against A0 and A0′, not only by totals. A knob is **effective** if it removes most of the ≥ 80-packet population (≥ 80 % fewer such frames than A0) and the loss falls with it by ≥ 2x in the affected minutes while the < 40-packet buckets' loss is unchanged — that bucket-specific pattern is the causal evidence the run is after. A knob **did not bite** if the tail is unchanged (then the driver ignored it; say so). **Drift** is flagged if A0 and A0′ differ by more than the O1/P5 session-to-session spread (their per-minute Pearson was 0.89-0.96; totals within ~10 %); if they do, the arms between them are read against the nearer bookend and the run says the environment moved. If one arm is clearly best, **repeat only A0 and that arm once more** (two more sessions) before writing the record, so the recommendation rests on two pairs.
