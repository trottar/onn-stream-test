# O1 task handoff — read the air from the Opal

Run only after `D-BASE-R5` is recorded in docs/memory/CURRENT.md (the per-minute loss series depends on it). Unattended, ask nothing.

**Why (from `D-BASE-P4`):** the onn exposes no retry, failure or airtime counter, so interference and channel contention are invisible from the client. The Opal is an OpenWrt-derived router; its `iw` can report per-station transmit retries and failures, received-packet drops, signal, and — if the driver supports `survey dump` — channel active/busy/receive/transmit time, which is airtime contention measured directly. `D080-D083` found the Opal's *packet capture* points blind during traffic; this task does not capture packets, it reads counters, which is a different path and may or may not work on the Siflower driver. Finding out is part of the task.

**Access and precautions — read before the first SSH command.** The user has installed a host-side key and an SSH alias so the Opal is reached as **`ssh opal`** (the alias lives in the host user's `~/.ssh/config`, outside the repository; it carries the address so that nothing here has to). **Read-only, without exception**: the only commands this task may run on the Opal are `iw` (`dev`, `info`, `station dump`, `survey dump`, `list`, `phy`), `ubus call` for read-only wifi status, `uci show wireless` (read only — never `uci set`, `uci commit`, `wifi`, `reboot`, `opkg`, or any write to `/etc`), `cat` of `/proc/net/dev`, `/proc/net/wireless`, `/proc/loadavg`, `/proc/meminfo`, `/sys/class/net/*/statistics/*`, `logread` (read), `date`, `uptime`, `iwinfo` if present, and `hostapd_cli` read-only status if present. Nothing is installed on the Opal, nothing is written to it, and the session must never print, store or log the Opal's password (it does not have it), its addresses, MACs, BSSIDs or SSIDs — redact station MACs to a stable per-run label such as `sta-A` before anything is written under evidence/. If Claude Code's tool permission refuses `ssh opal …`, stop at the first refusal, write the exact sampling script to evidence/o1_<date>/o1_opal_sample.sh so the user can run it by hand, and record INDETERMINATE; do not look for another way in.

**Two facts from the user's first `ssh opal "iw dev"` (2026-09-21), to build on and to check.** (1) This build's `iw dev` prints `noise` and `channel utilization` per AP interface directly — 5 GHz read 3.3 % idle, 2.4 GHz 23.3 % — so airtime is available even if `survey dump` is not; sample it every round. (2) Each radio also has a managed-mode interface (`sta0`, `sta1`) as GL.iNet firmware creates for a wifi uplink/repeater; both showed 0 dBm and 0 Mbit/s. Confirm with `iw dev sta1 link` and `iw dev sta0 link` that neither is associated — if the 5 GHz one is, the radio is time-shared with an uplink and that is a finding that outranks everything else in this task. Also record the Opal's load average at rest (1.08 was seen idle) and through the sessions.

**Inventory first (one minute).** `ssh opal iw dev` and `iw list` to name the 5 GHz interface the onn is on and whether the phy advertises survey support; `iw dev <5g> info` for channel, width and tx power; `uci show wireless` (read) for the configured channel, width, country and any `noscan`/`htmode` settings; one `iw dev <5g> station dump` and one `survey dump` to see which counters this driver actually populates — list them, and say which are zero or absent, as P4 did for the onn. If `station dump` shows no retries/failed and `survey dump` is unsupported, say so and still run the sessions for the interface and per-station counters that do exist.

**Sampling.** A host-side script runs `ssh opal` every 10 s (one connection per round; measure the round's cost and the Opal's load average before and during — if the Opal's load rises by more than 0.3 from sampling, thin to 20 s) and appends JSON lines: UTC time, the 5 GHz interface's `survey dump` (active/busy/rx/tx/ext-busy ms, noise), the onn's station row (signal, signal avg, tx bitrate, rx bitrate, tx packets/bytes, tx retries, tx failed, rx packets, rx drop misc, connected time, inactive time), the interface statistics from `/sys/class/net/<5g>/statistics/` (tx/rx packets, errors, dropped, and the wired LAN interface's too), the Opal's load and free memory, and any new `logread` lines mentioning wifi/hostapd/deauth/DFS/channel since the last round.

**Sessions.** Two 20-minute attract-mode sessions of the PS1 reference title, zero input, per TOOLS.md, BACK to end, teardown between, the sampler running 60 s before and after each. With `D-BASE-R5` installed, the heartbeat gives the per-minute loss series directly.

**Analysis.** Per minute: client loss (from the heartbeat deltas), forward-gap events, beside the Opal's channel busy fraction (busy/active), the onn's tx retries and tx failed deltas, rx drop deltas, signal, and any log events. Spearman of per-minute loss against each; the top-quartile loss minutes listed with their Opal readings; every Opal log event with the loss around it. **Pre-registered reading:** airtime contention is implicated if channel busy fraction or retry/failed deltas track loss (|rho| ≥ 0.5 over ≥ 40 minutes) and the loss-burst minutes carry visibly worse readings; the Opal's radio is implicated if loss tracks Opal-side tx failed or rx drops with busy fraction flat; neither is implicated if all Opal readings are flat through 10x loss swings — in which case the remaining suspects are the Opal's switching/forwarding between the wired port and the radio (the interface `dropped` counters speak to this) and the onn's receive path, and the record must say which of those the interface counters point at. State the levers for each outcome (channel, width, tx power, placement; or a different access point) and that choosing is the user's decision.
