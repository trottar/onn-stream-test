## B10 — the client under loss: freeze, ask for a keyframe, count

- **Settle from the code first:** what the client does today when an access unit is dropped (`sequence_gap_au_drops`, `incomplete_au_drops`): the next complete frame is queued to MediaCodec, which decodes it against references it never had — state it from the code; and how often the host sends an IDR today (≤ 41 frames, the C3-L2A-E2 cadence) and whether the host can insert one on demand (the actuator's IDR request path).
- **The design, hashed,** behind `debug.privyhub.loss_guard=1` (client) and `PRIVYHUB_LOSS_GUARD=1` (host):
  1. **the client, on a dropped access unit:** stop queuing non-IDR frames to the decoder and keep showing the last complete frame (a freeze) **until the next IDR**, then resume — and **send one `keyframe_request` datagram** on the controller socket (as B7's stall does) so the wait is one round trip, not up to 41 frames;
  2. **the host:** on `keyframe_request`, force an IDR at the next frame through the encoder's existing path (rate-limited: at most one per 500 ms, logged `keyframe_forced`); absent = ignored as today;
  3. **the counter the user's picture needs:** `frames_after_dropped_reference` — frames the decoder was asked to decode between a drop and the next IDR (today's behaviour: the corrupted ones; with the guard: 0 queued, the count of what *would* have been corrupted) — in the client report and the heartbeat, so a record can say "N corrupted frames" instead of "rendered".
- **The cost, stated:** a freeze of up to one round trip + the IDR's size instead of a corrupted picture; the IDR's bytes on the wire per request (the frame cap holds — D-BASE-P6a).
- Tests: the client's assembly with a fake decoder (the drop → no non-IDR queued → the IDR → resumed; the counter), the host's request path with a fake encoder control (one IDR, the rate limit); the APK built offline (B5 + B7 + this), pinned, NOT installed; CL-B9 (install + a `loss-1` cell with the guard on / off, the user watching) sketched.
