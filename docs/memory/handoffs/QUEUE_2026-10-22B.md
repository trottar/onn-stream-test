## B2 — the fast input hold

Read first: `E3_A3_RECOVERY_V2_ADOPTION_2026-10-09.md` and `E3_A3B_…` (recovery v2: `controller_silence` pauses at **+5.35 s**, resumes on `controller_return`; `client_output_silence`; `gave_up_saved`; the pause / resume primitives and the state they keep), `D_BASE_R3C_RECOVERY_SEMANTICS_…` (what a pause does to the core; the paused-load caveat), `companion/native_session_io.py` (the controller bridge: **does the client send controller packets continuously (~70 /s, state every tick) or only on change? Settle this from the code first** — the client in `PrivyHub/` too), the recovery module (`companion/recovery*.py` or wherever v2 lives), `UX_R3_…` §1 and §3.

- **If the client sends only on change, STOP B2 here and write it:** a hold on silence would pause whenever the player is still. Then B2 becomes "the client sends its controller state every tick behind a flag" first, and the hold after — write that task sketch in the record instead.
- **The design (if continuous):** `PRIVYHUB_INPUT_HOLD=<H ms>` (absent = today byte for byte; 0 or invalid = ignored, logged once). When no controller packet has arrived for H ms (default 250 when set) during an active stream, the host **pauses the core through recovery v2's own pause primitive and state** — never a blind `PAUSE_TOGGLE`, never a second actor: the hold is a second, faster trigger inside the same state machine, with its own reason `input_hold`, so v2's 5.35-s `controller_silence`, the client's `client_output_silence`, `gave_up_saved` and `controller_return` stay coherent (one paused state, one owner). **Resume on the first controller packet** (`input_release`), with the time held logged. A hold that lasts past v2's own threshold hands over to v2's existing path (no double pause, no double resume). Rate-limited so a flapping link cannot pause / resume faster than the core can follow (state it; e.g. a minimum hold of 2 frames and a cap on holds per minute, with the cap's exhaustion logged).
- **What it costs the player:** up to H ms of the game running without input (≈ 15 frames at 250 ms) instead of seconds; the picture freezes during the hold (the stream keeps sending the last frame — say what the encoder does on a paused core, from the code / E3-R1).
- **Proof:** unit tests with a fake clock (silence shorter than H → nothing; ≥ H → one hold; the first packet → release; a hold reaching v2's threshold → v2 owns it, exactly one pause row; the rate limit); the recovery suites green; flag absent = byte for byte. **No live run** (A's bench, B1's blackout cells, hold on / off).
- **The measure A will use, defined here:** **"unattended frames"** = host frames emitted while no controller packet had arrived for ≥ 250 ms, per blackout and per 10 min — the number the hold exists to cut. Write the reader (`tools/unattended_frames.py`) over the frame-size log and the control-gap log, and run it over UX-R1's and UX-R2's copies as the baseline (Sunday's and the death's numbers).
