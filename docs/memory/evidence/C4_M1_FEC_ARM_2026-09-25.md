## Step 0 — offline simulation (`c4_m1_simulate.py` → `c4_m1_simulation.txt`)

- **Corpus.** The replay used exactly the C4-D1 inputs: 38 sessions and
  their heartbeat windows, all still covered at 97-100 %.
- **Model.** For each post-FEC gap of b packets, the gap's offset is
  uniform over the offsets consistent with 8+1 having recovered none of it.
  Each scheme's expected recovery is then averaged over those offsets:
  - interleaved 8+1 recovers b = 2 fully, b = 3 by 1, b = 4 by 0.33, and
    b = 1 by 0 (a lost parity stays lost);
  - 8+2 recovers b = 1 by 1, b = 2 by 2, b = 3 by 0, and b = 4 by 0.67.
- **Assumptions.** Frame boundaries and the one-group-later parity are
  ignored, which makes the interleaving estimate an upper bound.

**How "at the corpus median" was read.** The phrase has three readings:

- (a) the median of per-session shares;
- (b) 1 − median after / median before;
- (c) median recovered / median lost.

A first pass on 44 sessions had shown (a) and (b) on either side of 40 %.
So it was decided **before** the 38-session numbers were seen that a scheme
passes only on every reading.

| scheme | (a) | (b) | (c) | ≥ 40 % on every reading |
| --- | ---: | ---: | ---: | --- |
| interleaved 8+1 | 39.3 % | 45.8 % | 41.4 % | **no** |
| 8+2 | 40.6 % | 48.0 % | 41.2 % | **yes** |

**→ BUILD 8+2.** It is the second candidate, reached only because the free
one missed.

## Step 1 — the scheme, built on a comparison path

**The stop rules did not trigger.**

- The client's FEC header has a version byte, and the receiver drops
  anything but version 1.
- Group repair lives in the FEC code, not in the H.264 reassembly.

**The relay** (`native_fec_relay.py` + the new `native_fec_rs.py`):

- The scheme is read from `PRIVYHUB_FEC_SCHEME` at start. Unset is today's
  scheme, and an unknown value reads `xor8_1`, flagged `env_ignored`.
- Under `xor8_2` the relay sends **today's v1 XOR parity unchanged**, then
  a **v2 datagram**. The v2 datagram has the same 23-byte header with a
  Reed-Solomon Q parity over GF(2^8) (0x11d, generator 2, RAID-6).
- It uses `bytes.translate` and big-int XOR, so there is no per-byte
  Python loop.
- `native_stream.encoder_overrides()` reads `any_override` true, with
  `fec_scheme_override`, while the variable is set.
- The profile is unchanged.

**The client** (`RtpH264Receiver.kt` + the new `FecRs82.kt`):

- It accepts version 2 and merges P and Q into one group entry, whichever
  arrives first.
- It then recovers one packet from Q when P was lost, or two packets from
  P + Q.
- The v1-only path is unchanged, and so are the counters and what each
  means per group. Q datagrams are not counted in the client's
  `fec_parity_packets` / `fec_groups_received`.

**Tests:**

- **Golden** (`c4_m1_golden.py`, `golden_*.txt`): the relay driven with
  synthetic RTP built from the recorded H.264 sample.
  - With the scheme unset, the output is **byte-identical to the
    unmodified relay's**: 986 datagrams, sha256 `d2081744…`.
  - Under `xor8_2`, the RTP and v1 parity bytes are identical, and one v2
    datagram follows each of the 130 groups.
- **Python** (`tools/test_fec_xor8_2.py`, 9/9, `python_codec_tests.txt`):
  - the golden check;
  - RTP and P identical under `xor8_2`;
  - the scheme is shown in status, and an unknown value is ignored;
  - every single loss recovers from Q when P is lost (all groups, all
    positions);
  - **every two-loss pattern recovers** (> 1,000 cases, consecutive or
    not);
  - the reference P equals the relay's;
  - three losses are not recovered;
  - the GF field is sound.
- **Kotlin JVM** (`FecRs82Test`, 6/6, `kotlin_FecRs82Test.xml`):
  - the Q bytes equal the Python encoder's (sha256 cross-check);
  - every single loss recovers from Q, and every pair recovers;
  - RTP-offset inputs work, three losses fail, and the field has inverses.
- **Build**: `py_compile` passes. `:app:assembleDebug` built the **arm APK
  `d2d855d82c30f986472a9ee839ef6b75f5102cb19900ef6c745a937a8eb87a79`**,
  installed with the device hash equal.
- **Adopted APK**: `f31b1c180c5d0849230860d2f5b7ab1b4a8637f7be56a7dcf1f71aba77668ae7`
  was kept at `runtime/c4_m1/`.

**Primary rule: NOT SHOWN.**

- A was lower in **1 of 3 pairs** (A2); the rule needs ≥ 2.
- The pooled A median was **3.08 against B's 4.47 = 69 %**; the rule needs
  ≤ 60 %.

**Cost rows: WITHIN NOISE on all five.** Spikes, fps, stale drops, max
gap and audio underruns each fall inside or better than the B range. The
max gap would need all three A holds above the worst B, and A2 and A3 are
within 6-9 ms of it.

**Recovery latency**: the client's `fec_max_hold_ms` was 14 / 14 / 14 in A
against 22 / 15 / 14 in B. Q follows P in the same group completion, so
there is no added completion delay.

**What the numbers say, as facts beside the rule:**

- **The second parity did what it was built for.** Unrecoverable groups
  fell to 0.25-0.50/min from 0.60-1.49/min, and recovered packets rose
  2-4×.
- **But the arm's streams lost 2-3× more packets before FEC**: 16.5-31.0
  against 6.6-11.4 per min. Post-FEC loss therefore landed in the same
  range.
- That is the concern `C4-D1` recorded before the arm was built: **k+2 adds
  a parity packet per group inside the same frame bursts that `P5`/`P6`
  located the loss in.** The arm added ~158K datagrams per hold, one per
  group, roughly +14 % on the ~1.16M datagrams a hold sends.
- **One night, on a low-loss path.** B ran at 2.9-4.9/min, under the < 10
  row, and the onn was cool. This does not show the arm would not help on
  a lossier, warm night, and it does not show it would.
