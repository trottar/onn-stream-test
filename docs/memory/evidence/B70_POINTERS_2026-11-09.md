## 1. The hub's pointer (host)

- **Read:** the Linux capture is `ffmpeg -f x11grab -framerate 60 -window_id <id> -i <display>`, with no `-draw_mouse`.
  ffmpeg's default draws the X cursor into every frame while the hub's pointer is over the game window: the "Linux
  one".
- **Built:** `-draw_mouse 0` as an x11grab input option, placed after `-framerate` and before `-window_id`. It comes
  from one helper, `_capture_pointer_args()`.
- **Off:** `PRIVYHUB_CAPTURE_POINTER=1` gives an empty splat: the argv is today's, byte for byte, and C5-M1's pinned
  string compares equal.
- **Scope:** every Linux capture start, including the in-place restart, the fast restarts, the in-place step and the
  ladder's rungs, because they all use the one builder. The Windows `gdigrab` path is untouched.
- An X cursor is drawn by the server, not into a window's pixels, so the GameCube window's own cursor goes too.
- **Live at the companion's next restart** (A's HOME-10 stage 1); no drop-in.

## 2. The onn's pointer and the touchpad (client)

- **Read:** the stream activity handed every motion to the controller path and then to Android. It set no pointer icon
  and asked no pointer capture. So the pads' touchpads, which are a pointer device to Android, moved Android's pointer
  over the game. A touchpad gets Android's own touch-spot presentation: "their own different style".
- **Built:** `PointerGuard.kt` (pure; fake-host tests), used by `NativeStreamActivity`:
  - **consumed:** any event whose source carries the pointer class bit, or is `SOURCE_TOUCHPAD` / `SOURCE_MOUSE` /
    `SOURCE_MOUSE_RELATIVE` / `SOURCE_TOUCH_NAVIGATION`. That covers:
    - motion (hover, scroll, swipes), in `dispatchGenericMotionEvent` before the controller path;
    - presses and clicks, in `dispatchTouchEvent`;
    - pointer-source keys (Android's mouse-button fallbacks, e.g. a secondary click's Back), in `dispatchKeyEvent`
      **before the Back handling**, so the touchpad cannot leave the game;
    - the trackball.
  - The last two sources (mouse-relative, touch-navigation) go beyond the queue's three named ones (disclosed in the
    design).
  - **The pointer hidden:** the null pointer icon on the root and every view under it, and on the decor view.
  - **The pointer captured** (`requestPointerCapture`) whenever the game's window gains focus, with a listener that
    swallows every captured event. **The capture is what hides the touchpad's own style**, which an icon alone does
    not; so the queue's "pointer-capture API if needed" is needed here. Android releases it when the focus goes.
  - **Untouched:** the remote's D-pad / OK / Back (`SOURCE_DPAD | SOURCE_KEYBOARD`), the pads' buttons
    (`SOURCE_GAMEPAD | SOURCE_KEYBOARD`) and their sticks / hat (`SOURCE_JOYSTICK`). None of these carries a pointer
    bit; the tests show they pass.
- **The DualShock / DualSense touchpad press, settled:** it arrives from the touchpad's own input device as a pointer
  click. It is not a pad button: the gamepad device reports no key for it, and no PrivyHub layout (PS1, N64,
  GameCube) uses it. **Default: swallowed with the rest of the touchpad. Listed** (KNOWN_ISSUES): ask if it is ever
  wanted as a button.
- **Off:** `debug.privyhub.pointer_hide=0` → nothing consumed, no icon, no capture.
