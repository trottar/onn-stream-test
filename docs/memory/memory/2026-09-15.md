## Linux/onn integrated E2E diagnosis

The first real integrated Linux/onn game launch crossed the emulator/runtime
boundary successfully: PS1 launched, an existing save loaded, Linux controller
preflight worked under the temporary uinput ACL, the exact managed X11 window
was found, and VAAPI encoded the native stream near the intended 60 fps.

Android did not automatically enter the native stream because MainActivity
still requires the Windows-only `host_window_policy.window_found` preflight.
Linux's native backend later found the correct X11 window, proving this is a
separate handoff compatibility bug.

After manual entry, NativeStreamActivity failed stabilization with severe
transport symptoms. Fresh decoder evidence showed substantial video loss,
audio loss/starvation, stale-output drops, low delivered/rendered FPS and long
output/decode gaps. Host telemetry then showed a video send-call maximum near
785 ms. The independent Linux audio sender, already nonblocking and SCHED_RR
priority 1, simultaneously accumulated large send-error counts and long cadence
gaps.

Repeated `/proc/net/snmp` before/after probes showed thousands of UDP
`SndbufErrors` and `RcvbufErrors` per short run while interface
`tx_errors`/`tx_dropped` remained unchanged. Increasing `rmem_max`/`wmem_max`
to 4 MiB so 2 MiB application socket requests were honored did not improve the
stream and worsened sender behavior, falsifying small socket ceilings as the
root cause.

The host Wi-Fi adapter was identified as USB Realtek RTL8822BU (`0bda:b812`),
driver `rtw_8822bu`, at 5000 Mb/s USB speed. USB runtime autosuspend is disabled
and has never suspended. Disabling rtw88 deep-LPS did not materially change the
failure. Kernel logs showed repeated `firmware failed to leave lps state` plus a
register read timeout. A controlled NetworkManager profile test successfully
disabled ordinary Wi-Fi powersave; LPS/register warnings disappeared during
that run, but UDP send/receive-buffer errors and audio send failures remained
severe. Ordinary LPS is therefore a real secondary driver issue but not the
primary cause of stream collapse.

The next diagnostic is the preserved standalone Linux -> onn idle UDP acceptance
probe, outside RetroArch/MediaCodec/production streaming. The first Linux shell
wrapper failed before sending with `ONN_ADDRESS_DISCOVERY_FAILED`; correct only
the local address-discovery seam, without asking for or exposing an IP.

Separate cleanup: PS1 runtime reported missing `scph5501.bin`; restore it before
final PS1 acceptance, but it is not responsible for current stream transport
failure.

can restart on a new random port.

existing diagnostic. From a stale/private host it scans ports on that single
host, attempts ADB only on listening candidates, validates through the existing
pairing, refreshes private caches, and keeps all network-bearing values out of
shareable evidence. Runtime validation is pending.

The v4 ephemeral-port recovery probe did not recover the paired onn. The user
then connected locally with `adb connect` using the current private endpoint;

an ephemeral range of 32768-60999. V5 now caches host/range state from a valid
online session, restricts future stale-endpoint scanning to that one host and
range, and prompts for repair/re-pair followed by one retry only after automatic
recovery is exhausted. Production installer parity remains deferred pending
runtime validation.
