# 2026-09-19

Two Phase C work items closed, one memory correction. No roadmap item was
unblocked by any of it.

## C3.L2c — low-latency decode. Installed, falsified, rolled back.

`AvcLowLatencyDecoder.kt` was changed to request `MediaFormat.KEY_LOW_LATENCY`
unconditionally instead of honoring `c2.realtek.video.avc.decoder`'s own
`FEATURE_LowLatency` self-report, which says unsupported. Real
`sh ./gradlew :app:assembleDebug --no-daemon` build, installed on device, one
gameplay session measured.

The gate removal worked: `low_latency_enabled` flipped true — the only session
on record where it is true.

Per-frame decode improved sharply and the worst stall did not. Against the
seven ordinary sessions recorded on the same device the same day:

| | low-latency session | seven ordinary sessions |
| --- | ---: | --- |
| `max_codec_ms` | 107 | 140-433 |
| `spike_20_ms` | 147 | 775-3,260 |
| `spike_50_ms` | 19 | 91-314 |
| `spike_250_ms` | 0 | 0-4 |
| **`max_output_gap_ms`** | **385** | 126-424 |

385 ms is the second worst of the eight. In every ordinary session the gap
tracks `max_codec_ms` to within ~10 ms; here it exceeded it by 278 ms. The
user's own assessment of the build was "trash" and matched the measurement.

Reverted to the capability-gated behavior; `AvcLowLatencyDecoder.kt` restored
to its exact predecessor bytes, SHA-256
`22038e355f85bb8330d900bae64c37db54c902d4affdef12be4810bb03271c07`, verified.
First post-revert session: `low_latency_enabled: false`, 221 ms gap.

Durable consequence, larger than the candidate: **`max_codec_ms` is not a
valid proxy for `max_output_gap_ms`**. Filed in `MEMORY.md`. Records:
`evidence/C3_L2C_LOW_LATENCY_DECODE_FALSIFIED_2026-09-19.md`,
`patches/C3-L2C_LOW_LATENCY_DECODE_ENABLE.md`.

## C3.L3 — Linux fixed-bitrate port and characterization. Closed.

The probe scripts called a Windows-only implementation built around WGC
replacement capture (`hwnd`, `_wgc_bridge_path()`) that fails immediately on
Linux. Ported by reusing the validated `C3.L1`/`C3.L1R1` encoder-only restart
primitive rather than building a second mechanism:
`run_c3_linux_fixed_bitrate_cycle()` in
`companion/diagnostics/c3_linux_actuator_probe.py` restarts the single
x11grab/VAAPI ffmpeg process at a caller-chosen bitrate through
`_build_linux_ffmpeg_command`'s pre-existing, previously uncalled
`bitrate_kbps`/`max_bitrate_kbps` overrides, emitting the same
`privyhub_c3_fixed_bitrate_cycle_v1` schema the probe scripts already expect.
`native_stream.py`'s three `diagnostic_c3_fixed_bitrate_*_cycle` wrappers
dispatch by platform the way `diagnostic_c3_actuator_continuity_cycle` already
did. The Windows implementation was not modified. Record:
`patches/C3-L3_LINUX_FIXED_BITRATE_PORT.md`.

Ten trigger/finalize cycles across three runs at 5000/5500/6000 kbps. Zero
`cycle_fec_send_errors_delta`, `cycle_audio_send_errors_delta` and
`cycle_controller_bad_packets_delta` in every one; `waiting_for_idr` returned
to false every time. The mechanism is COMPLETE / RUNTIME VALIDATED.

Characterization, `decoder_max_output_gap_ms`:

| bitrate | run 1 | run 2 | run 3 | band |
| --- | ---: | ---: | ---: | --- |
| 5000 kbps | 367 | 292 | 242 | 125 ms |
| 5500 kbps | 219 | 584 | 335 | 365 ms |
| 6000 kbps | 331 | 291 | 307 | **40 ms** |

6000 kbps is the most consistent and never exceeded 331 ms, across sessions
of 21.1s, 77.2s and 64.8s. 5500 kbps produced both the best and the worst
single result; its 584 ms session traces to one 417 ms resync-to-IDR event
with 52 packets dropped waiting for IDR.

All of it is transport and decoder timing. No perceptual quality was measured,
so no bitrate is accepted as a fallback level. Record:
`evidence/C3_L3_LINUX_FIXED_BITRATE_CHARACTERIZATION_2026-09-19.md`.

## C3-L3R1 — memory correction

`CURRENT.md`, the `C3.L3` evidence file and `docs/KNOWN_ISSUES.md` were
written stating that run 3's 6000 kbps result was invalid and a rerun was
owed. The rerun had already been taken and was valid; its result was on disk
in `logs/streaming/c3_fixed_6000_characterization.json` when that text was
written. Consequences of the omission, all corrected here:

- 6000 kbps was judged on two samples instead of three, which produced the
  conclusion that **5000 kbps was the most consistent bitrate**. With the
  third sample (307 ms) the bands are 125 / 365 / 40 ms and **6000 kbps is
  the most consistent** — the opposite reading;
- the decoder-session file blamed for the finalize bug,
  `native_decoder_20260919_055703_163.json`, was described as "a fresh
  decoder-session file consistent with a real, separate 6000 kbps play
  session ... written 18.8s before the 6000 finalize ran". It is the **5500
  kbps** session — duration 66,638 ms, gap 335 ms, the 5500 kbps numbers
  exactly — and it was written 391 s, not 18.8 s, before the 6000 kbps
  finalize. It is the file the buggy attempt wrongly matched, not the file it
  should have matched;
- the valid 6000 kbps session is `native_decoder_20260919_060325_369.json`,
  64,840 ms, named by the probe itself in
  `payload.decoder_session_log`, written 9.4 s before its finalize;
- `CURRENT.md` carried a Next Action asking for a run that had already
  happened, and was 13,378 bytes — over the 10 KB soft limit — with
  implementation narrative that belongs in a patch record. Rewritten to
  8,856 bytes;
- `roadmap/STATUS.md` and `MEMORY.md` had not been updated at all by the
  `C3.L2c`/`C3.L3` work. Both brought current;
- no evidence record existed for `C3.L2c` — the result lived only in its
  install record. Promoted, with the numbers re-derived from raw decoder JSON.

Every figure in the corrections was re-derived from
`logs/games/decoder_sessions/*.json` and
`logs/streaming/c3_fixed_*_characterization.{json,txt}`, not transcribed.

Record: `patches/C3-L3R1_CHARACTERIZATION_CORRECTION.md`.

## Defects recorded, not fixed

- `tools/probe_c3_fixed_*_characterization.py --finalize` matched the wrong
  decoder-session file once, when run immediately after another bitrate's
  finalize. **Intermittent** — the 6000 kbps rerun in the same sequence
  matched correctly. Not root-caused. Workaround: check
  `payload.decoder_session_log` and `session_duration_ms` against the intended
  session before using any finalize result. Companion-side `C3.L3` code is not
  implicated.
- `slow_events_marked` is emitted as an empty array while
  `slow_event_retained_marked` reports 30 of 64. Open since `C3.L2b`'s first
  use. Not blocking.
- File-bridge writes to `docs/memory/*.md` read back stale several times
  during the day's work. Isolated single-file writes, and re-reading the raw
  file before trusting it, worked around it every time. Never affected code
  files.
