# Chat and Memory Communication Protocol

<!-- PRIVYHUB_D128_DELIVERY_SAFETY:BEGIN -->
## Interactive-shell delivery invariant

User-facing Linux patch blocks must not call `exit`, must not enable persistent
shell options such as `set -euo pipefail` in the interactive user shell, and
must not rely on shell termination for error handling. Wrap the complete
operation in a function and use function-local `return` codes, then print the
result after the function is unset. A command block that closes the terminal is
a delivery failure even when repository rollback succeeds.
<!-- PRIVYHUB_D128_DELIVERY_SAFETY:END -->

## Platform-command invariant

Before sending an executable command block, match it to the active host, shell,
and authoritative worktree. The current PrivyHub prototype host is Linux/Bash
with authoritative worktree `~/Projects/onn-stream-test`. Legacy
Windows PowerShell and `L:\Projects\onn-stream-test` examples are historical
only unless the user explicitly says the active environment has changed.

A command block that targets the wrong platform is a delivery failure even when
the underlying patch is correct.

## Patch-stage invariant

Treat the installed checkpoint as the only current GUI/runtime truth. Do not ask
the user to locate or exercise a feature introduced by a patch until all prior
stages have completed successfully: installer/build -> APK installation ->
companion restart when required -> runtime action -> diagnostic/evidence.

Never describe a patch-only control as though it already exists in the user's
current GUI.

## Idempotent-install invariant

Marker presence is not installation proof. A marker-bearing working tree may
select an idempotent validation path, but that path must verify exact
deterministic generated bytes against the expected predecessor and rerun every
required compile/build/diff/memory gate before reporting `INSTALLED SUCCESSFULLY`.


## How we work with the user

Summarized from `handoffs/COWORK_HANDOFF_2026-10-05.md`, "How we work (the
user's rules; keep every one)"; the off-site stage words from
`handoffs/G4-S4_OFFSITE_FREE_PLAY_TASK.md` and
`evidence/G4_S4_OFFSITE_FREE_PLAY_2026-10-24.md` §10. The source wins where
this summary is shorter.

- **The bridge.** The user is remote (a Windows PC, PowerShell, SSH into the
  Linux host) and cannot paste into Claude Code from the PC. The planning
  chat writes the task into `docs/memory/handoffs/<NAME>_TASK.md` and a
  one-line prompt into a `_cowork_prompt*.txt` file at the repo root (one per
  session, e.g. `_cowork_prompt_b.txt`), reads it back from the host, and only
  then says it is ready. The user types "Read `<prompt file>` in the repo root
  and follow it as my prompt." and later says "Code is done".
- **Verify from the raw artifacts** (the evidence dir, `sha256sum -c` on the
  manifest, the pre-registration hashes, the summaries recomputed where cheap)
  before telling the user anything is true.
- **Nothing is committed by a session.** Commits and pushes are the user's;
  the commit line comes from the task's `logs/<task>_git_status.txt`.
- **Hand steps:** numbered, one paste-ready block each, saying where (the
  PowerShell SSH window on the PC), what the user should see, and what a reply
  must contain to count. Prefer a helper script over a multi-step hand route.
  Outputs go to files under `logs/` that the session reads; nothing is pasted.
  Never ask for anything findable in `docs/memory/`. Keep replies short.
- **Privacy:** never write down or ask for an IP, MAC, SSID, BSSID, ADB
  endpoint, serial or credential; placeholders only. The router is read-only;
  its band, width and channel are the user's hand changes. ROMs, BIOS, keys,
  logs, savestates and APKs stay out of git.
- **Sessions cannot run `nft` or real `sudo`**; the user runs those tools.
- **Pre-registered rules** are written before the data and never changed
  after. **Nothing perceptual is a gate**: the user's own look is recorded as
  their words and decides adoption. **Nothing is adopted without the user's
  explicit word in chat**; the task quotes it.
- **Never hand the user a run to start while a Claude Code queue is running.**
- **Say so plainly when a prediction fails.**
- **Off-site stage words.** In an off-site session only the user's exact
  stage word changes the stage: "launch" starts it, "stop" means touch STOP
  now, "Code is done" (once home) starts the read. Anything else is a status
  report: "At home in onn now" meant the onn's home screen, and reading it as
  "back home" ended G4-S4's attempt 1. If a message is ambiguous, read the
  live state first (overlay path, game active), then ask; never close the
  session on a guess.

## Start of substantial work

Read:

1. `AGENTS.md`;
2. `CURRENT.md`;
3. only CURRENT-linked records relevant to the task.

Consult `MEMORY.md` selectively. Read handoffs/history only when needed.

## During work

Put the chronology and the proof in the task's `evidence/` record (the dated
memory logs ended 2026-10-10) or the relevant investigation. Put durable conclusions in `MEMORY.md` only when they
are expected to matter beyond the current task.

Do not append completed patch narratives to active-state files.

## End of meaningful work

Update:

- the task's `evidence/` record;
- `CURRENT.md` if objective/state/next action changed;
- relevant evidence/investigation/roadmap/decision records;
- `MEMORY.md` only for durable knowledge;
- `CURRENT_HANDOFF.md` only as a compact transfer note.

Follow `MAINTENANCE.md` when thresholds or semantic triggers fire.

## Patch behavior

Memory changes travel with the same work that establishes the code or evidence
change, left in the working tree for the user's commit.
