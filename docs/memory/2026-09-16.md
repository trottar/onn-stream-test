## Persistent uinput and realtime-priority fix

The udev ownership rule already existed, but `/dev/uinput` was not reliably
registered after reboot because the module was not guaranteed to load.

Persistent module loading was added:

`/etc/modules-load.d/99-privyhub-uinput.conf`

containing:

`uinput`

After reboot, `/dev/uinput` existed with PrivyHub ownership and the required
realtime-priority allowance remained available (`ulimit -r` reported `1`).

Classification: persistent controller prerequisites resolved. Older memory
listing these as open production-permission gaps is superseded for the current
development host.

## Temporary routed topology and ExpressVPN packet filter

Tested path:

`GL-iNet -> Wi-Fi -> Windows PC -> Ethernet -> Linux PC`

Windows could directly reach the Linux companion listener, but onn/GL-iNet
traffic did not consistently reach Linux.

ICS rebinding produced unstable alternating behavior and was rejected as the
solution.

Packet-level Windows tracing showed GL-iNet packets arriving on Wi-Fi and
reaching the Windows filtering/TCP-IP layers without corresponding Ethernet
egress. Disabling Windows Firewall did not repair the path.

Adapter inspection then found the ExpressVPN NDIS packet filter
`expressvpn-pkf` attached to both physical adapters. Disabling that binding on
the Wi-Fi and Ethernet adapters immediately restored the routed path.

After that correction:

- companion connected;
- Crash Bandicoot launched;
- native game streaming worked.

Classification: ExpressVPN physical-adapter filtering was a real routed-path
blocker in this temporary topology.

## Controller isolation

Initial symptom: controller buttons worked, movement did not.

Transport diagnostics showed thousands of controller packets with zero send
errors and nonzero motion events.

Linux created:

`PrivyHub Virtual Gamepad P1`

RetroArch detected it in port 1.

The generated autoconfig mapped the left stick to axis 0/1, and the virtual
device exposed `ABS_X`, `ABS_Y`, `ABS_RX`, `ABS_RY`, `ABS_Z`, `ABS_RZ`,
`ABS_HAT0X`, and `ABS_HAT0Y`.

Live event monitoring showed changing `EV_ABS` values on `ABS_X` and `ABS_Y`,
including near-full-scale positive and negative motion.

Therefore the remaining movement problem is not Android transport, Linux
permissions, uinput creation, or analog generation. The next investigation is
RetroArch PS1 controller mode/core/session behavior: digital PlayStation pad
versus DualShock/analog mode.

## ExpressVPN follow-up: VPN tunnel versus downstream Linux Internet

The physical `expressvpn-pkf` bindings were confirmed disabled on both Wi-Fi and
Ethernet.

With ExpressVPN disconnected:

- Windows Internet worked;
- Linux Internet worked;
- PrivyHub local routing worked.

With ExpressVPN connected:

- Windows Internet worked;
- Linux could still reach its Windows gateway;
- Linux external Internet routing failed.

Windows IP forwarding remained enabled in both states. No active `NetNat`
object or ICS sharing configuration was present.

Route inspection showed the Windows Internet route using the physical Wi-Fi
path with the VPN disconnected and the ExpressVPN interface with the VPN
connected.

Classification: forwarded Linux traffic does not successfully traverse the
ExpressVPN tunnel in this temporary Windows-as-router topology. This is deferred
by design. When Linux requires upstream Internet during development, disconnect
ExpressVPN.

No literal network addresses are retained in durable memory.

## D-084 — Linux A8 named-profile portability bug

A8.2 was originally designed and runtime-validated on:

`Android canonical XUSB/PHI1 -> Windows ViGEm X360 -> RetroArch XInput`.

D-076 later migrated Linux controller output to PrivyHub uinput devices and
project-owned udev autoconfig while intentionally preserving canonical PHI1/XUSB
semantics.

The A8 schema/editor survived that migration correctly because it stores
semantic control names. The final runtime adapter did not: it still converted
semantic names through `A8_XINPUT_*` numeric tables on Linux.

Repository evidence:

- Linux uinput maps physical A/B/X/Y to
  BTN_SOUTH/BTN_EAST/BTN_WEST/BTN_NORTH.
- The validated Linux RetroArch udev profile resolves canonical physical
  A/B/X/Y to joystick indices 0/1/3/2.
- Linux LT/RT are axes +2/+5.
- Linux right stick X/Y are axes 3/4.
- Linux D-pad is axes 6/7.
- Linux Y axes use the opposite raw sign from the old XInput adapter because
  D-076 inverts canonical XInput Y when emitting Linux ABS_Y/ABS_RY.

The existing A8 deterministic probe also retained Windows expectations, so it
could not detect this Linux portability regression.

Decision: preserve A8 storage/editor semantics and add a host-specific
translation table at the final RetroArch adapter boundary. Update the existing
probe rather than creating a parallel profile system or diagnostic path.

Status after patch packaging: deterministic/source validation complete;
real onn gameplay validation pending.

## D-085 — older-memory controller reconciliation and udev D-pad fix

The controller regression was re-audited against the older Phase-A/D-076 record.

Key correction to prior reasoning:
- Windows controller behavior had real gameplay acceptance.
- Linux D-076 host validation was narrower. P1-P4 were created/configured,
  PHI1 updates arrived, meta controls worked, Save/Load worked, and teardown was
  graceful, but D-076 still required real gameplay controls for full acceptance.

Raw Baseline 42 remains useful only at its measured layer. It observed:
- ABS_X/Y -> joystick axes 0/1
- ABS_Z -> 2
- ABS_RX/RY -> 3/4
- ABS_RZ -> 5
- ABS_HAT0X/Y -> 6/7

The project incorrectly copied the hat indexes into RetroArch udev autoconfig as
ordinary directional axes. RetroArch udev uses `h0up/down/left/right` for those
hat directions.

D-085 corrects the four project udev profiles and the D-084 Linux A8 translator.
No transport or uinput event-generation change is made.

This explains the observed Crash split without requiring a transport theory:
face buttons can work while D-pad movement is absent. Analog movement in a PS1
title remains a separate Digital/DualShock controller-mode question.

## D-087 — Linux PS1 multitap Config-path portability

With Multitap enabled, launch failed before RetroArch with:
`Beetle PSX HW core-options file is unavailable for multitap launch`.

Linux Beetle seed at `~/.config/retroarch/config/Beetle PSX HW/Beetle PSX HW.opt`,
with Port 1 and Port 2 multitap keys present and disabled.

Current source still used `runtime executable parent / config / Beetle PSX HW`
and required that path under the project root. Decision: preserve Windows
behavior and add Linux XDG/default-user Config-root selection. Existing `.opt`
transformation remains unchanged.
