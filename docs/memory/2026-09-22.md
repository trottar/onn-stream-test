## `D-BASE-P6a` — the 90 KB frame cap becomes the profile default

### The user's half, first, because it is what made this a decision

On 2026-09-22 the user ran the `A1` arm themselves, played for about a
minute, and reported **no stutters** and that they **"could barely tell it
was over the LAN."** That is **a user-stated perceptual result, not
instrument evidence**, and it is recorded in their words and not upgraded
anywhere. `D-BASE-P6` had measured everything except the picture; this is
the picture, and with it the user adopted the setting.

### What changed

**The cap moved from an environment override into the profile.**
`NativeStreamProfile` gains `max_frame_size_bytes` (default **0** =
uncapped, so any profile not declaring it behaves exactly as before), and
`native_game_720p60_reference` declares **90,000**. It sits beside width,
height, fps, bitrate, GOP, B-frames and FEC group size because it is the
same kind of fact: **a transport parameter wearing an encoder's clothes.**
The burst that overflows the AP's queue *is* the frame, so bounding the
frame is what makes this profile deliverable over one wireless hop.

**Three source states, and the third needed new code.**

| environment | cap | argv | source | `any_override` |
| --- | ---: | --- | --- | --- |
| unset | 90,000 | flag present | `profile` | **false** |
| `=60000` | 60,000 | flag present | the variable | true |
| **`=0`** | **uncapped** | **flag absent** | the variable | true |

`_env_int` folded "unset" and "0" into one answer, so `_env_int_or_none`
was added beside it — **`=0` is the documented way to re-run the `P6`
baseline**, and that only works if zero is a value rather than an absence.

**`any_override` changed meaning deliberately**: the profile being in force
is no longer an override, so false now means *nothing but the profile
decided the argv*. That is the "default is in force" reading from here on.
`default_max_frame_size_bytes` and `uncapped` were added so a status read
says which source won without anyone inferring it.

**Scope held.** `-bufsize` untouched at 7000k and `PRIVYHUB_ENC_BUFSIZE_K`
still default off (`P6` measured VBV and it was **not** adopted — 3x the
loss). No pacing, FEC or client change. **The deferred Windows NVENC
builder ignores the field and logs one line saying so** rather than
inventing a translation with no measurement behind it.

### Two things learned

**Removing the tail removed the content-lock.** V1's per-minute loss
correlates with nothing — not with the other capped sessions (Pearson
−0.291, −0.064), not with the uncapped ones (−0.546, −0.456). `O1` found
the loss reproduced at **0.964** session to session because the attract
loop replayed the same large frames in the same minutes. **The lock was a
property of the tail**, and with the tail gone the residual 249 packets are
not content-driven. What the residual *is* is `D-BASE-S3`'s question.

**The byte cap and the packet threshold agree by arithmetic.** 90,438 bytes
is ~76-79 packets, because a large frame's packets run near the 1,188-byte
payload maximum rather than the 1,066-byte session mean. That is why a
90,000-byte cap lands just under the 80-packet threshold and why every
capped session reports `max_packets` 77.

## `D-BASE-S3` — three hours on the adopted cap

### The finding that outranks the rest

**Two frames in 180 minutes exceeded 90,000 bytes — by 11 and 9 bytes.**
The driver's `max_frame_size` is a **target, not a hard ceiling**; `P6`'s
60 KB arm had already measured 60,092. It does not touch the mechanism:
those frames are **~76 packets** against a **>= 80** threshold, the
session maximum was **77 packets**, and **no minute had a frame at 80+**.
The consequence is for testing, not for the adoption — **a check must
allow a small tolerance rather than assert `<= 90000` exactly.**

### The cap holds and the loss keeps falling

**977 losses over three hours = 5.4/min**, lower than any 20-minute capped
session (15.4 / 20.3 / 12.4) and roughly **25x below uncapped**. Over the
same first 20 minutes `S3` lost **163** against 308 / 408 / 249. **0
sequence resyncs, 0 SSRC changes, 0 onn socket drops**, fps **59.96**,
spikes 26.7/min, max forward gap **27 packets**, bitrate 6,928.7 kbps.
Hourly **380 / 340 / 253** — 1.50x, under the 2.0 drift flag, and trending
**down**.

### The residual is a floor

The pre-registered question, and the answer is unambiguous. Across **1,080
ten-second** and **180 per-minute** windows, Spearman of loss against max
packets per frame, max frame bytes, frames >= 40, mean packets, frame
count, receive rate and Opal channel utilization is **under 0.08 in every
case**. The bucketed table is **flat** — 0.80 / 1.05 / 0.85 loss per
window across `< 40`, 40-59 and 60-79 — where uncapped it rose **14-fold**
into the `>= 80` bucket that no longer exists.

**So a tighter cap is not a live lever**, which also explains why `P6`'s
60 KB arm tied on loss: there is no frame-size signal left to remove.
0.011 % of packets go missing with no per-window structure, and nothing in
these instruments distinguishes the windows that lose from those that do
not. **The loss column is closed at this level.**

### Rotation, thermals, memory

**Both bounded logs rotated twice with zero lost rows** — the frame-size
series has **0 discontinuities across 10,801 one-second rows** and the
heartbeat slice holds 5,382 lines at 2,001-2,031 ms. First multi-hour test
of the `P6` log, and it is clean.

**Thermals plateau** as `T1` found: k10temp 53/54/55 °C by third, amdgpu
edge 43/43/44, power 18/18/19 W, encoder CPU 27 % flat.

**`S2`'s memory finding does not fully reproduce, and that is said rather
than smoothed.** RetroArch grew **+140.2 MB** over three hours of which

Majority file-backed (75.5 %), so "warm-up, not a leak" survives in its

## `D-BASE-P7` — `prolonged_starvation_events` named, at last

Record: `evidence/D_BASE_P7_STARVATION_COUNTER_2026-09-22.md`. Patch:
`patches/D-BASE-P7_AUDIO_HEARTBEAT_COUNTERS.md`. Classification:
**CHARACTERIZED**. Nothing about audio behaviour was changed, and the
counter was **not renamed** — the handoff asked what it measures, and a
rename on top of a fresh answer would have broken every older record
that quotes it.

### What the counter actually counts

Read from the client source first, before any measurement. In
`NativeAudioReceiver.kt` the starvation poll runs every `PACKET_MS` = 5
ms while the queue is empty, and the increment is **latched**:

```kotlin
if (starvationPackets > FADE_CONCEAL_PACKETS && !starvationEpisodeCounted) {
    prolongedStarvationEvents.incrementAndGet()
    starvationEpisodeCounted = true
}
```

So it is **one increment per starvation episode, not per poll**, and the
threshold is `FADE_CONCEAL_PACKETS` = 2 packets = **~15 ms** of empty
queue. A rate of 32/min is 32 holes a minute, not 32 polls.

### The measurement

One 20-minute session on the adopted profile, 600 heartbeats at schema
**v3**, against the ten new audio fields — of which the decisive one is
`audio_max_arrival_gap_ms`, the largest inter-arrival gap **within that
tick's window**, read-and-reset so each tick is independent.

- Spearman rho **+0.684** against the per-tick max audio arrival gap.
- Spearman rho **+0.020** against audio loss — essentially nothing.
- Packet deficit per event averages **+0.54 of ~400** expected packets.

The third number is the one that settles it: when an event fires, the
packets are **not missing**. They arrive. They arrive **late**. This is
a jitter counter wearing a loss counter's name.

### Where the hole is, and where it is not

**93 % of ticks peak in the 50-69 ms band** — a hole of roughly one GOP
of audio, recurring about once every two seconds. The host-side pacer
was sampled over the same session and paces to **5.0 ms mean, 5.08 ms
maximum**: the sender emits a clean 5 ms cadence and something between
the sender and the mixer bunches it. **Sender pacing is closed by
measurement, not by argument.**

The rate is a **property of the path**: 75.9/min on the old PC-wired
arm, **32.0/min** on the capped Opal path. It halved when only the path
changed, with no client change in between.

### How to read it, and the one lever left

32/min sounds alarming and is not: the same session recorded **4 actual
underruns in 20 minutes**. The concealment cushion absorbs nearly every
hole. The only client-side lever is a **deeper cushion** — target 3
packets / 15 ms against a p90 hole of 60 ms means roughly **+45 ms of
audio latency**, which is a real cost on a game stream and is **not**
being spent without the user's word.

**Still open:** what produces the 55-60 ms hole. One maximum per 2 s
tick cannot be aligned against the video burst, the AP's beacon, or a
client-side stall; answering it needs per-packet arrival timestamps,
which is a separate instrument and a separate authorization.

### The trap that cost a session

The first P7 session recorded **no audio fields at all**. The client was
sending them and `native_stream_heartbeat.py` was ready to store them,
but `companion/plugins/games.py`'s `native-stream-heartbeat` handler
carries an **explicit integer whitelist**, and a key not on it is
**dropped silently** — no warning, no error, an otherwise healthy
heartbeat. **Adding a heartbeat field takes two edits, not one.** The
session was abandoned and re-run once, within the two-retry rule.

Also re-confirmed from `TOOLS.md`: `pkill -f "<pattern>"` matches the
shell's own wrapper and kills the caller (exit 144). Select pids
explicitly with `ps -eo pid,comm,args | awk ...` instead.

### Housekeeping

Schema bumped to `privyhub_native_stream_heartbeat_v3`; `AUDIO_FIELDS`
added to `native_stream_heartbeat.py` and to the plugin whitelist;
`NativeAudioMetrics` gained `maxArrivalGapMs` with a session atomic that
is never reset and a window atomic that is read-and-reset;
`NativeStreamActivity.audioQuery()` omits the whole block when the
receiver is absent, so a missing field stays a finding rather than a
zero — the `D-BASE-P4` rule.

## `H2-PREP` — the display path, read while there is still a screen

Record: `evidence/H2_PREP_HOST_DISPLAY_INVENTORY_2026-09-22.md`. Harness
under `evidence/h2_prep_2026-09-22/`. **Read-only**: no `sudo`, no
`xrandr --output`, nothing created or edited under `/etc`, no unit
enabled, no reboot. Nothing on the host changed.

### Three findings that change `H2`, none of them about the plug

1. **`openssh-server` is not installed.** Not disabled — absent.
   `/usr/sbin/sshd` does not exist, there is no `ssh`/`sshd` unit file,
   and nothing listens on 22. The SSH *client* is there (OpenSSH 10.0p2,
   which is why `ssh opal` works for the router sampling); the server is a
   separate package. **`H1` has not been started**, and once the monitor
   is gone there is no console at all.
2. **There is no autologin.** Every `autologin-*` line in
   `/etc/lightdm/lightdm.conf` is commented out. A reboot stops at the
   LightDM greeter — no X session, no RetroArch window, nothing for
   `x11grab` to attach to. `H2`'s check 5, "survives a power cycle with
   nothing but the plug", **cannot pass** as things stand.
3. **Nothing starts the companion at boot and `Linger=no`.** No
   project-owned unit, empty crontab, user processes killed at logout.
   The answer to "what would an unattended power cycle leave running" is
   **nothing** — that is the finding, not a gap in the search.

### The path itself

A real **X11** session (`XDG_SESSION_TYPE=x11`, no Wayland compositor on
the host), LightDM → XFCE, X running as root under
`lightdm --session-child`. So `x11grab` attaches to the X server directly
and nothing about the capture changes headless.

**The connector, in both spellings:** X's **`DisplayPort-0`** is DRM's
**`card0-DP-1`**, and the two namings are **off by one** on this host
(X `DisplayPort-N` = DRM `DP-(N+1)`). Route (a), an `xorg.conf.d`
`Monitor` section, needs the X spelling; route (b), a kernel `video=`
parameter, needs the DRM one. There is **no `/etc/X11/xorg.conf`, an
empty `xorg.conf.d/`, and no Monitor/Screen/Device section anywhere**, so
route (a) is the route this stack is set up for — but `H2` verifies it by
restarting LightDM and reading `xrandr`, rather than trusting it.

**The current monitor tops out at 1440x900.** `1920x1080` is in neither
its `xrandr` list nor `/sys/class/drm/card0-DP-1/modes`. Panel is a Dell
1909W (vendor/model from the EDID; the serial was deliberately not
recorded). One more detail: `xrandr --verbose` reports
`subconnector: VGA` — the monitor is on an **active DP→VGA adapter**, so
the plug will be a different *kind* of sink on the same wire.

**Two things that will not need fixing:** blanking is already off
(`DPMS is Disabled`, screensaver `timeout: 0`, `xfce4-power-manager` DPMS
timers all 0), and there is **no saved desktop display profile** to
override an X config — XFCE's `displays.xml` holds only
`ActiveProfile=Default`. `light-locker` *is* running, which is worth a
glance during the cutover.

### The capture is a window, not the screen

`_select_capture_target()` runs `xdotool search --onlyvisible --pid
<managed RetroArch pid>` for up to 2 s and **fails closed** — it raises
rather than falling back to whole-desktop capture. The last session
captured an **879x720** window and scaled/padded it to 1280x720, on a
1440x900 desktop. So the desktop resolution is not the capture
resolution, `--onlyvisible` means X-mapped rather than physically
displayed (so it should survive the plug), and the failure message
*"Whole-desktop capture is intentionally disabled"* should be read as
**no window**, not as a capture fault.

`_linux_display()` reads `DISPLAY` from the environment and nowhere else.
The running companion carries `DISPLAY=:0.0` inherited from the X session
and `PPID=1` (nohup'd). A companion started from a bare SSH shell, or
from a unit without `Environment=DISPLAY=:0`, would find no display.

### ADB across a host reboot

The host key pair `~/.android/adbkey{,.pub}` persists, and the onn's
"always allow this computer" is bound to it — **no re-approval on the TV**
for a host reboot. What is lost is the adb server on 5037 and the
connection with it. `TOOLS.md` documents no `adb connect`/`tcpip`
procedure at all, so `H2` is asked to **record the exact reconnect command
it used**; that is a gap to fill rather than something this task could
look up.

### Redaction

`h2_prep_redact.py` strips the EDID hex block (it carries the panel serial
in its 0xff descriptor), the root filesystem UUID, IPv4/IPv6 addresses,
MACs and the adb serial. Its `--check` mode was run against the redacted
file and reported **0 residual matches**; the unredacted intermediate was
deleted and never written under `docs/`. The IPv6 pattern requires `::`
or four or more colons so it cannot eat an `HH:MM:SS` timestamp — the
`O1` bug, not repeated.

### The number that changes how the loss column is read

**3 s of outage cost 2 348 lost packets. 15 s cost 22. 150 s cost 40.**

Not an artifact — it is the recovery. N3 fired no restart, so one ffmpeg and
one SSRC ran across the gap, and the receiver met a 2 336-packet forward jump
on return: a `sequence_resync`, counted as loss. N15 and N150 restarted, and a
new ffmpeg means a **new SSRC**, so the return is an `ssrc_change` with
`jump_packets: 0` — **not counted as loss at all**.

So every loss-per-minute figure in the `D-BASE` column under-counts outages
that triggered a restart, and the longer the outage the more likely it
restarted. **`max_output_gap_ms` is the honest column**: it reproduced all
three faults to within 60 ms. Through N150's whole 150 s, `rx_packets` sat
frozen at 26 537 and `rendered_frames` at 1 898 — the drop was total.

### The two defects the prompt half then produced

Diagnosed from logs only — one hypothesis, one probe, no run.

**Both are one root cause.** `native-stream-stop` pauses the game and keeps
the session, by design. So after N150, RetroArch `pid 7827` stayed alive and
paused, and everything afterwards was routed **into that session**. The
launcher tile could only resolve to `recovery-resume`, which loads a state
into the running process — it reports **"Loaded"** and opens nothing.
**There is no `POST /plugins/games/launch` after 11:20:49** in the companion
access log, and no second game log was ever written. That settles defect 1.

Defect 2 needed a probe, because the obvious one fails: **frame size cannot
tell a static source from a moving one here** — the encoder is CBR and pads,
and the looping session's mean frame size (14 483 B) is indistinguishable
from live gameplay (14 613 / 14 749 / 14 680). What does work is **IDR-size
dispersion**: an IDR is an intra-coded still, so its size measures the
picture's complexity, and a source cycling through a few pictures must
produce a few byte-exactly repeating IDR sizes.

| window | IDR size spread | distinct |
| --- | --- | --- |
| post-run, after resume | **3 686 B** | 5 of 8 s |
| three R3b gameplay windows | 52 923-74 242 B | 73-95 % |
| N150's paused window | **0 B** (66 150 B x 110 s) | 1 of 110 s |

The paused window is the calibration that makes it readable. The post-run
session is **14-20x narrower than any gameplay window but not zero** — a real
short loop, not a freeze and not gameplay, beginning **one second** after
`PAUSE_TOGGLE -> PLAYING`. The client is exonerated by its own report:
`lost_packets 0`, `sequence_resyncs 0`, 59.85 fps, `dropped_frames 0`.

**What is not resolved**: *why* the core cycles. Either the ordering — the
state was loaded into a **paused** core which then sat paused 86 s before
resuming — or Beetle PSX HW restoring a state under GL hardware rendering.
The logs cannot separate them; that needs a run, and this task was not one.
