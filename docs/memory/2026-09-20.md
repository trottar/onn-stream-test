# 2026-09-20

Phase C suspended. The premise it was built on is falsified.

## C3.L3a Part 2 ran, and the probe has three defects

The gameplay acceptance session ran to completion: 8 traversals, 16
transitions, zero FEC/audio/controller deltas across the whole session. That
lifecycle result is real and is a `C3.L4` readiness answer — repeated
transitions do not degrade a subsystem that a single one does not.

Two of the report's headline numbers are probe defects, not findings:

- **the mark-association window anchors on sequence start.** A ramp runs ~11 s,
  so its 2.5 s window closes long before it finishes. Four marks landed
  1.5-1.9 s after a sequence *ended* — textbook reaction lags — and all were
  scored "attributed to nothing". The bias runs toward making transitions look
  invisible, which is the worst possible direction;
- **telemetry field paths were wrong.** They were built from
  `c2_stream_telemetry_runtime.json`, which is the C2 probe's own output
  artifact, not the endpoint response. The live shape is `receiver.recent_fps`,
  not `measurements.receiver_recent_fps`. Every sample returned None, the
  settle test required fps near 60, so settling was never measured. "8/8 never
  settled" measures nothing.
- **the picture rating used an unanchored 1-5 scale.** The user rated out of
  10; the prompt showed a bare `[1-5]` with no anchors and no statement of what
  1 or 5 meant. Their answers were 5/10, 3/10 and 2/10 for 6000/5500/5000, not
  5/5, 3/5 and 2/5. Read correctly the ratings and the accept/reject booleans
  agree; the "contradiction" was an artifact of assuming the wrong scale.

All raw marks and per-cycle timings are retained in the state file, so the
session is re-scorable without replaying.

## The baseline is not healthy and never has been

Aggregating every decoder session on disk of >= 15 s — 47 sessions,
2026-09-16 to 2026-09-20, all at the 7000 kbps reference, most with no actuator
activity:

| metric | median | worst |
| --- | ---: | ---: |
| decode spikes >20 ms / min | 2,506 | 2,723 |
| rendered fps | ~56 | 34 |
| max output gap | 345 ms | 7,341 ms |
| lost packets / min | 199 | 2,094 |
| audio underruns / min | 155 | 2,555 |

At 60 fps a minute holds 3,600 frames and the budget is 16.7 ms, so **~70% of
every frame misses budget, in every session.** The stream has never reached
60 fps. Full record:
`evidence/BASELINE_STREAM_HEALTH_2026-09-20.md`.

## The regression the user felt is real, and it is in the tail

Split by client code epoch: across **21 sessions before the 2026-09-19
flattening the worst stall was 338 ms**; after, it is **7,341 ms**, with 3,783,
1,997, 1,271 and 1,062 also on the board. The median moved 231 -> 392 ms. The
tail rose about twentyfold.

Session length does not explain it: a 16.7-minute pre-flatten session maxed at
331 ms, a 14.2-minute post session at 7,341 ms.

Decode spikes, fps and stale drops are **identical across every epoch**, so
neither the flattening nor `C3.L2b` caused the chronic decode fault. That one
predates all of Phase C.

Epoch B — flattened, pre-`C3.L2b` — has four sessions, two of them
sub-30-second fragments. **Too thin to separate the two changes.** `C3.L2b` is
the stronger suspect on mechanism: it added per-frame and per-packet
bookkeeping to `AvcLowLatencyDecoder` and `RtpH264Receiver`, i.e. the hot path,
while `ANDROID-FLAT` changed only directory layout and left Kotlin package
declarations, and therefore bytecode semantics, untouched. The flattening did
force a full rebuild, so it is not excluded.

The irony is on the record: the instrumentation added to measure stalls is the
prime suspect for causing them.

## Mechanism for the decode fault

The decoder holds **11-13 frames in flight** — 180-220 ms of pipeline depth
before any decode work is counted — while `latest_feed_delay_ms` is 0 and
`input_waits` stays in the tens. The client feeds promptly and is never
starved; the decoder is buffering for throughput, which is right for video
playback and wrong for interactive streaming. `stale_output_drops` are frames
decoded too late to display: 2,461 of 50,515 in the long session.

`MediaFormat.KEY_LOW_LATENCY` is the API for exactly this, and
`c2.realtek.video.avc.decoder` reports it unsupported.

## C3.L2c is reopened, on the wrong-statistic error

The single low-latency session is the best on record on every distributional
metric: **159 spikes/min against 1,828-2,723 for all 46 others**, best fps
(59.0), lowest drop rate (0.15%), `stale_output_drops` 16 against 191 in the
comparable non-low-latency session.

It was rolled back because `max_output_gap_ms` moved 359 -> 385 — one
worst-case sample per session. The falsification record correctly noted that
`max_codec_ms` is not a proxy for `max_output_gap_ms`; the error was the
unstated converse, that **`max_output_gap_ms` is not a proxy for how the stream
plays either.** One sample overruled thousands.

## Decision: baseline before adaptation

Phase C is **suspended, not failed**. None of the three faults is a bandwidth
fault, so adaptive bitrate control adjusts the one variable that is not the
problem. The user's requirement, recorded because it is the actual
requirement: seamless lag-free local play, with remote play unreachable
without it — a link that stalls 7.3 s locally has no headroom for WAN latency,
jitter and real loss.

The target is numeric and distributional, with no perceptual gate: spikes
>20 ms under 200/min, fps at or above 59.5, max gap at or under 100 ms, stale
drops under 20/min, loss under 10/min, audio underruns under 5/min.

Order of work: (1) settle the tail regression with a one-variable `C3.L2b`
revert; (2) fix the decoder path, reopening `C3.L2c` judged on the
distribution, and attack the 11-13 frame in-flight depth which the low-latency
flag alone did not fix; (3) record the physical link type, then transport;
(4) audio; (5) the pre-registered client decision.

**Pre-registered:** if after steps 1-3 a healthy decode path on a wired link
cannot reach under 200 spikes/min and 59.5 fps, the onn is the ceiling and the
client changes. Written down now so it is reached by measurement rather than
attrition.

Decision: `decisions/D-BASE_BASELINE_BEFORE_ADAPTATION.md`. Investigation:
`investigations/BASELINE_STREAM_HEALTH.md`. Record:
`patches/D-BASE_BASELINE_STREAM_HEALTH.md`.

## What Phase C keeps

The Linux actuator is real, measured and correct. `C3.L3a` Part 1 showed
chained ladder transitions are clean on both host and client. The work is not
discarded — it is a mechanism awaiting a reason, and it resumes when the
baseline justifies adaptation.
