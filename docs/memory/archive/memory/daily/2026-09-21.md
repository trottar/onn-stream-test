## `C5a` — count the rejected IDRs. INDETERMINATE.

The `C5` §4 probe, built and installed: session counters
`idr_aus_rejected_waiting_for_idr` and
`non_idr_aus_dropped_waiting_for_idr`, plus `rejected_idr_aus` /
`dropped_non_idr_aus` on each `first_idr_after_discontinuity` row. Counting
only — the increments sit in the marker block's corrupt branch, which
already discards every AU it sees, and run only while `waitingForIdr`. The
receiver's output does not differ by one byte. APK `c3252ab5…c718`.

**The probe is sound. The fault injection is not, and the reason matters.**
The task specified the `D-BASE-R3` SIGSTOP substitute in short form —
0.3 s stalls of the encoder at 30/60/90/120 s — on the premise, inherited
from the R3a record, that these produce 720/984/480-packet sequence jumps.
They do not. **A stopped encoder emits nothing**, so it burns no RTP
sequence numbers, and on SIGCONT the sequence resumes contiguous. The stall
is a gap in *time*, not in *sequence*. R3a's jumps came from a different
mechanism: longer holds that tripped recovery into a C3.L1 encoder restart,
which spawns a new encoder with a new SSRC and a fresh sequence base.

The runtime data says it directly. Three 150 s sessions, real loss on the
link (122 / 51 / 228 packets, 12 / 7 / 14 forward-gap events), and the
**largest forward gap in any of them was 47 packets** against
`RESYNC_FORWARD_GAP_PACKETS` = 128. Zero sequence resyncs, zero
discontinuities, every counter 0. `desync_pause` absent from the recovery
log throughout, as the task required — the pulses stayed below `DESYNC_MS`.

Those zeros are uninformative rather than evidence. `waitingForIdr`
initialises `true`, so the counters could in principle fire at session
start — but the encoder starts *with* the client here, so the first access
unit the receiver ever sees is the stream's opening IDR
(`first_clean_idr_ms` 577 / 577 / 607, nothing before it).

**So one further session was run to separate "nothing to count" from
"counter never reached"** — labelled CTRL throughout, and a deliberate step
past the task's stated injection, taken so the record would not rest on
unexercised code. It replaces the pulse with the already-validated C3.L1
encoder-only restart at the same four marks: four `ssrc_change` resyncs at
**18 / 22 / 22 / 24 ms**, every row carrying both new fields, all with
`rejected_idr_aus` 0. The resync path executed, the instrumentation is
wired, and the 18-24 ms confirms C5's 18-65 ms actuator band on independent
runs. It changes no classification — an `ssrc_change` is the fast path by
construction and cannot test the `> 250 ms` limb.

Four discontinuities against a pre-registered floor of six, none over
250 ms: **INDETERMINATE on both counts.** The counters stay in the tree for
the corpus to accumulate. The bounded fallback is **not** implemented; it
is a separate decision.

**What is still owed.** A real >= 128-packet loss run on the wire. SIGSTOP
of the encoder is ruled out at any pulse length short of tripping a
restart; the C3.L1 restart is ruled out by construction. The nftables plan
remains the only injection that would work and **still cannot run — no
non-interactive root on this host**. One untried alternative is noted in
the record and **not attempted**: SIGSTOP the *companion*, so the FEC relay
stops forwarding while the encoder keeps producing into the socket and the
kernel drops datagrams off a full receive queue. It also stops the control
server and the audio and controller paths, so it needs its own risk read
and its own authorization.

The first R2 attempt aborted at the PLAYING gate: BACK ends the client
session but leaves the game **active and paused** on the host, so the
relaunch POST was a no-op. The harness now stops the game before each
launch. R1 was unaffected and stands as recorded.

## `D-BASE-P2b` — the startup hold is exonerated; `D-BASE-P2a` is RUNTIME VALIDATED.

Ten 120 s attract sessions, five matched pairs, **strictly alternating
hold-off / hold-on starting with hold-off**, two APKs from one source
differing only in `STARTUP_REAL_PCM_TIMEOUT_MS` (0 against 3,000). The
patch was not reverted and the source ends at 3,000; `startup_wait_ms`
proves each arm in its own report (0 with `timed_out: true` for hold-off,
2,050-2,199 with `timed_out: false` for hold-on). One session was rejected
and re-run — the pilot, for two discontinuities inside 30 s; none of the
ten in the battery was rejected, all had zero discontinuities.

**The question was drift or side effect. The answer is neither.** Pooled
Spearman of `prolonged_starvation_events` against run index is **-0.036**,
so there is no drift through the night. The sign test puts hold-on above
hold-off in **3 of 5** pairs — not 5 of 5 — and the two largest deltas run

`D-BASE-P2a` attributed to the hold, where `D-BASE-P2`'s 134-146 was a
narrower sample of it. By the letter of the pre-registered reading this is
the "mixed" outcome, but it is mixed in one direction, and a direct control
settles the question more strongly than the drift hypothesis would have.

**The mechanism P2a proposed is not there.** `avg_queue_residence_ms`
medians are 27.70 (off) and 27.62 (on) across a 27.3-28.2 spread both arms
share; `max_queue_residence_ms` medians are 49 in both. The hold changes
when the track starts, not where the queue settles.

**Both of P2a's misses are closed**, so `D-BASE-P2a` is reclassified

this link both arms clear the fps bar (median rendered fps **59.53** off,

result replicated on five fresh pairs — median **276** with the hold off
against **19** with it on, the hold-off range 241-363 sitting inside P2's
pre-fix 201-399.

A note on the fps column: `video.recent_fps` is an instantaneous spot
reading and ranged **43.8 to 71.6** across these ten sessions. It is
useless at this resolution. `D-BASE-P2a` and `D-BASE-P2` both used
`rendered_frames / duration_s`, so their 59.38 and 59.16 figures stand and
are not corrected.

**What is still open is `prolonged_starvation_events` itself** — a second
phenomenon since `D-BASE-P2`, now also known to be insensitive to the

## `D-BASE-P3` — pace the sender and see (unattended)

Record: `evidence/D_BASE_P3_SENDER_PACING_2026-09-21.md`. Patch:
`patches/D-BASE-P3_FEC_RELAY_SENDER_PACING.md`. Reports, relay captures,
harness, analysis, the offline check and SHA-256s under
`evidence/d_base_p3_2026-09-21/`.

**The question, from `B2` and `R3a`.** On the production path the loss is
still bursty (4.46 packets per gap event) and a 3 s stall's resume burst
dropped 690 packets with no restart — packets minted by the host and lost
before the onn's decoder. The encoder emits each frame's packets back to
back at line rate, so every frame is a micro-burst into the Opal's wireless
queue. If the ordinary loss is that queue overflowing, spreading a frame's
packets should cut loss and burst size sharply; if it is air, nothing.

**The instrument.** `PRIVYHUB_FEC_PACING_US` — the **environment**, read in
`NativeVideoFecRelay.start()`, **default 0** — queues a frame's packets by
RTP timestamp and sends one every N µs from a dedicated thread, parity
directly after the group it protects, clamped to
`8000 µs / packets-in-frame` so everything is out within **8 ms of the
frame's first packet arriving**. Off is the old path **byte-for-byte**: an
offline check drives the same synthetic frames through both and asserts
identical emitted bytes, identical order, and equal `rtp_packets`,
`parity_packets`, `groups`, `skipped_packets`, `send_calls`, `send_errors`
and `sent_bytes`.

**`time.sleep` was measured before being chosen, and rejected.** It carries
a ~55 µs overshoot floor on this host — `sleep(150 µs)` returns after a
median 205.5 µs — so it cannot place a 150 µs gap. A busy-wait on
`perf_counter_ns` lands at 150.1 µs p50, 150.3 max, so the pacer sleeps
only while more than 300 µs remains and busy-waits the last ~200.

**One correction the offline check caught.** The first version anchored the
send schedule on the first packet's *arrival*; because a frame is only
queued once its marker lands and waking the sender costs more again, the
early packets were already due and went out back to back — achieved p50
**7.5 µs instead of 150**. The schedule now anchors on the moment the
sender thread starts the frame, with the budget still measured from
arrival, so the 8 ms latency bound is unchanged.

**Fifteen 120 s attract-mode sessions, zero input, strictly alternating**,
the companion restarted for every one with the port confirmed free, the
serving pid confirmed to be the one just launched, and the relay's reported
`configured_us` confirmed before the stream opened (D-068). Ten at 150 µs
(five pairs, starting off), then five at 400 µs alternating and **ending
off**. **0 sessions rejected** — none carried a discontinuity in its first
30 s, or at all — so nothing was re-run. `send_errors` 0 in all fifteen.

**The result is INDETERMINATE and pacing is not adopted.** Loss/min fell in
**3 of 5** pairs where the pre-registration wanted 4; the medians fell
**1.72x** (loss) and **1.70x** (packets per gap) against a 2x bar; and
**`spike_20_ms`/min rose in 5 of 5 pairs**, which the criterion forbids
outright. It is not ruled out either — packets per gap fell in **4 of 5**
and the median maximum forward gap **halved, 16 → 8**. Mixed, and reported
as mixed.

**The one reproducible result of the run is a cost, not a gain:** spikes
**42.7 → 60.1 per minute, +41 %**, in every one of the seven paced
sessions. Worst-case latency did not rise — `max_rx_to_decode_ms` median
**137 → 112** — and fps held at 59.67, so what moved is the body of the
latency distribution, exactly where spreading a frame over ~2 ms would move
it. **And it does not scale**: at 400 µs the achieved spacing is only
**187.5 µs**, because the budget clamps **30 %** of frames, and loss fell
in **0 of 2** pairs.

**What bounds the null, and it bounds it hard.** Spacing is capped at
`8000 / packets-in-frame`, so a frame is clamped above **53 packets** at
150 µs and above **20** at 400. The mean frame here is **15.85 packets**
including parity and **11 %** exceed 53 — the IDRs and large P-frames.
**Those are precisely the frames a queue-overflow account blames, and they
are the ones the 8 ms budget refuses to spread at the requested rate.**
Pacing was therefore tested hardest where it applies least. Separately, the
off arm swung **1.8 to 35.2 loss/min inside one hour** on one link with
nothing changed: interleaving removed `B2`'s time-of-day confound and a
minute-scale one took its place, and five pairs cannot resolve 1.7x against
it. **Adopting pacing is a product decision for the user — the cost is
measured, the benefit is not established.**

**The onn's receive buffer, recorded once as asked.**
`RtpH264Receiver.kt:573` requests **2 MiB** and **the granted value is
exposed nowhere** — nothing reads `receiveBufferSize` back and it is in no
heartbeat and no report, so it stays unknown from the client, which was not
changed. Read-only on the device: `rmem_max` **8,388,608** and
`rmem_default` **229,376**, so the request is inside the kernel cap and is
not clamped there.

**The knob ends the run at 0.** It is set nowhere in the repository, in no
service unit and in no harness that outlives the run; `S3off`, the last
session in run order, records `fec_pacing.enabled: false`.

**The `pgrep -f` trap from `TOOLS.md` bit the harness's first draft.** Its
own `ps | awk` selector matched the `/bin/bash -c` wrapper whose command
line contained the harness text, and killing it took out the shell
(exit 144) before the file was written. The harness now selects the

## `D-BASE-P4` — is it the air? (unattended)

Record: `evidence/D_BASE_P4_AIR_TELEMETRY_2026-09-21.md`. Samples,
harvests, heartbeat slices, reports, scripts and SHA-256s under
`evidence/d_base_p4_2026-09-21/`. **No code change anywhere** — the sampler

stated the onn was on the Opal's 5 GHz SSID; `dumpsys wifi` confirms it —
**5180 MHz, channel 36, 80 MHz wide** (`channelWidth = 2`, a code and not
MHz), 802.11ac, ceiling **866 Mbps**, supplicant `COMPLETED` and **never
re-associated** in any of seven sessions. Had it been on 2.4 GHz that alone
would have been the finding and the run would have stopped there.

`dumpsys wifi` costs **368-387 ms of onn CPU** — over the task's 300 ms bar
and far too expensive to run beside a 60 fps decode. Rather than thin it to
20 s, the expensive dump was kept out of the sessions entirely: the live

keeps its own radio series anyway** — a `WifiScoreReport` CSV of **3,600
rows at ~3 s covering about three hours**, append-only and wall-clock

at 3 s resolution having cost the run nothing. Device local time is
**UTC−4**; the offset is read from the device and applied. Every stored
line is redacted of MACs, BSSIDs, quoted SSIDs and addresses.

**Seven sessions: six of 120 s and one of 20 minutes**, zero input, per
`TOOLS.md`, sampler running 30 s before and after each, companion restarted
between, the `D-BASE-P3` pacing knob confirmed **0** every time. **Nothing
was rejected** — all seven completed, and not one carried a discontinuity.

**The answer is no, and it is not close.** Loss/min swung **1.4 → 105 — a
74x range — while the radio sat still**: RSSI spanned **5 dB in total**
across 639 three-second samples, median **−66 dBm in every single
session**, and **not one scan of any kind** was logged inside any session
window. Inside the 20-minute session, at **n = 597** heartbeat ticks, the
client's receive rate against RSSI gives **rho = −0.022**, against Tx link
speed **−0.001**, against Rx link speed **−0.001**. The thirty ticks (5.0 %)
that fell more than 10 % below median rate **every one sit at RSSI −65 or
−66**, indistinguishable from the rest.

One session-level figure crossed the 0.5 bar — link quality at **+0.786**,
n = 7 — and **it is discounted rather than banked**: the 5 % critical value
at n = 7 is about 0.79, link quality on this driver is a monotone rescaling
of the RSSI that reads **+0.000**, and the sign is backwards, saying better
quality goes with more loss.

**Half the pre-registered test could not be run at all.** This device
exposes **no retry, failure, airtime or channel-occupancy counter**:
`tx_retry`, `tx_bad` and `bcnCnt` are identically 0 across all 3,600
score-report rows, `total_tx_retries`/`total_tx_bad` likewise across 440
usability entries, every `/proc/net/wireless` discard column and the
missed-beacon count are 0, `noise` reads −256, `channel_utilization_ratio`
is a **constant 15** and `total_cca_busy_freq_time_ms` is 0. `iw` and
`wpa_cli` are not present. **Signal strength, association, link rate and
scanning are excluded; interference and airtime are simply invisible from
this client** — and those are exactly where co-channel interference would
show. Recording them as absences, never as zeros.

**The 20-minute session is the substantive find.** It lost **2,114 packets
— 105/min at 14.89 packets per gap** — against 3.0-7.0 packets per gap in
the two-minute sessions, with the same radio readings. **The loss is
episodic: bigger bursts accumulate over a longer observation, and a
two-minute window frequently misses them.** That accounts for `D-BASE-P3`'s
1.8-35.2 control-arm swing as sampling variance far better than anything
about the radio, and it means **short sessions are the wrong instrument for
the loss column** — future runs on loss should be sized accordingly.

**A per-minute loss series was attempted and abandoned, and the failure is
recorded rather than hidden.** `loss(window) = Δ(relay rtp) − Δ(client rx)`
uses two real counters, but the client's is visible only through the 2 s
heartbeat and must be interpolated against an ~830 packet/s stream. Noise

3.0** — a 29x ratio — and individual windows land **negative**, which a
loss count cannot. Session totals reconcile (5 / 173 / 220 against reported

Loss stays per session. The single instrument that would most improve a
future run here is a **per-tick loss counter in the client**, which this
task forbade adding.

**Levers, all the user's and none of them code.** Band and background
scanning are already where you would put them — 5 GHz, and no scan fires
during a session, so there is nothing to disable. **Channel 36 and the
80 MHz width are the untested ones**: channel 36 is the bottom of UNII-1 and
a common default, 80 MHz spans channels 36-48, and each is a single Opal
setting. Placement would raise a link that runs **195-260 Mbps against an
866 Mbps ceiling at −66 dBm**, but the data does not say it would buy less
loss, since loss does not track RSSI. **The measurement's own
recommendation is different: instrument the Opal side or use a client that
reports retries**, because this one cannot answer what remains.

## `D-BASE-R5` — the receiver's loss counters in the heartbeat (unattended)

Record: `evidence/D_BASE_R5_HEARTBEAT_LOSS_COUNTERS_2026-09-21.md`. Patch:
`patches/D-BASE-R5_HEARTBEAT_LOSS_COUNTERS.md`. Report, reconstructed

`evidence/d_base_r5_2026-09-21/`. **RUNTIME VALIDATED** — every check
passed.

**Why.** `D-BASE-P4` left the loss column episodic and unmeasurable at any
resolution finer than a whole session: the receiver's counters existed only
in the end-of-session report, and deriving a series from host-sent minus
client-received put the noise at **86 packets per 10 s window against a
3.0-packet signal**. The receiver already kept every counter needed. This
put them in the 2 s heartbeat that already existed.

**The change is small on purpose.** One touch point in the client — the
heartbeat query string gains seven fields read from **the same
`receiver.snapshot()` the function already took** for `rx_packets`. No new
sampling, no new thread, no change to what the receiver counts or to the
heartbeat's cadence. The companion passes them through unchanged under
schema **`privyhub_native_stream_heartbeat_v2`**, and
`native-stream-status` gained `loss_per_min_recent`.

**Checked offline before spending a build**, which earned its keep:
`loss_per_min_recent` got the arithmetic exact (2 lost per 2 s tick →
**60.0/min** over a 60.0 s window), **confined its window to the current
session** when `elapsed_ms` restarted at zero — without that guard a delta
across a session boundary comes out negative — and returned **None rather
than 0** for a client too old to send the counters and for a log holding
one heartbeat. It also needed its own 64 KiB tail read: a 60 s window at
~465 bytes a line does not fit the existing 8 KiB.

**Validation: one 20-minute attract-mode session, zero input.** 597
heartbeats, cadence 2,005-2,511 ms with **no interval over 4 s**, so the
series has no holes.

- **All 597 carry all seven fields**, one schema throughout.
- **All seven loss counters at the last heartbeat match the report
  exactly** — `lost_packets` 2,218 = 2,218, and the same for
  `lost_packets_in_resyncs`, `forward_gap_events`,
  `max_forward_gap_packets`, `stream_resyncs`, `fec_recovered_packets`,
  `fec_unrecoverable_groups`. `rx_packets` differs by 1,310 **and should**:
  1,641 ms of stream followed the last heartbeat.
- **The series accounts for the report to the packet**: 2,212 in the series
  + 6 before the first heartbeat + 0 after the last = **2,218**.

**What it showed on first use.** Per-minute loss inside one session: **4,
9, 159, 5, 230, 161, 303, 0, 78, 72, 128, 152, 203, 2, 146, 0, 87, 228,
236, 7** — median 87, **minimum 0, maximum 303**, burst minutes 4, 6, 12,
17 and 18. Beside it the radio, from a post-session `WifiScoreReport`
harvest: RSSI **−65 to −67** across the whole session and `txLinkSpeed`
**260 in twenty of the twenty-one minutes**. **Minute 6 lost 303 packets
across 34 gap events; minute 15 lost none — at the same RSSI and the same
link speed.** That is `D-BASE-P4`'s finding reproduced at sixty times the
resolution with a direct measurement rather than an inferred one, and it
settles that the loss is **episodic within a session**, not only between
sessions.

**Live watching works.** `loss_per_min_recent` sampled six times during the
session read **158, 205, 76, 125, 24 and 87 per minute**, each on a
60.2-60.3 s window of 31 heartbeats.

**It cost nothing that shows.** The heartbeat line grew **276 → 465
bytes**, a 69 % increase, and `spike_20_ms`/min came out **51.5** — inside
`D-BASE-P4`'s seven-session range of 40.6-62.4 — with fps 59.70, max output
gap 343 ms and no discontinuities.

~453 to **~819 KB/h**, so the heartbeat log crossed 4 MiB **17.9 minutes
into the session** — **the first time rotation has run against real
traffic**, which `KNOWN_ISSUES` has carried as untested since `D-BASE-R4`.
It lost nothing: sequence step **1**, elapsed step **2,007 ms**, exactly one
interval. The 4 MiB fill time is now **~5.0 hours**, not ~9.

### Three counter traps, each of which would have been read as a measurement

The `D-BASE-P4` rule — absences are never zeros — earned its keep again.

1. **`survey dump` does not accumulate on this driver.** `channel active
   time` reads a fixed **29-30 ms** on every call, after 46 hours of
   uptime, and `channel receive time`, `channel transmit time` and
   `extension channel busy time` are **absent entirely**. It is an
   instantaneous 30 ms window, **not a counter**; differencing it would
   have produced pure noise dressed as airtime.
2. **`channel utilization` on `iw dev <if> info` is that same window,
   rounded.** 3.3 % is exactly 1 ms of 30, 6.6 % is 2 of 30 — the figure is
   quantised in **3.33 % steps**, and the radio is observed **30 ms in
   every 10,000, a 0.3 % duty cycle**. The mean over many rounds is a fair
   estimate of occupancy; it cannot see contention shorter than seconds.
   **The user's first look, "5 GHz 3.3 % idle against 2.4 GHz 23.3 %", was
   utilization, not idle** — 3.3 % is one quantum above zero, a *quiet*
   channel, the opposite of the worry it raised.
3. **`tx failed` is not independent of `tx retries`.** Their difference
   held at **6,790 → 6,792 across four hours and 240,000 retries**, so a
   `tx failed` delta just recovers the retry delta. **Retry exhaustion —
   the air's own way of dropping a frame — cannot be read on this driver**,
   and that is the single most important gap in the run.

the onn; `iw list` advertises no survey capability; `hostapd_cli` is
absent, `iwinfo` and `ubus` present. What *is* live and usable:

## `D-BASE-P5` — which queue drops the burst (unattended)

### The question `O1` left

`O1` located the loss at a per-frame micro-burst meeting a queue and left
two standing: the AP's per-station wireless queue and the onn's own
receive path. This run separates them with three instruments on one clock.

### The one code change, and it counts only

`native_fec_relay.py` now closes a frame on its marker packet — or on a
timestamp change, counted **separately** as `unmarked_frames` — and files
its packet count into a one-second bucket, with an exact
packets-per-frame histogram for percentiles and a 1,800-second ring.
A **separate 1 Hz writer thread** appends
`logs/games/native_frame_sizes.jsonl`, so **the forwarding thread never
waits on the filesystem**. Rotation reuses `games.log_rotation` at 4 MiB
keeping 3 into the existing `stream_log_archive/`, so retention needed no
change. **Nothing forwards, delays, reorders or drops differently and
pacing stayed at 0**, confirmed in both sessions' status.

Cost, measured over 200,000 calls: **0.36 us per packet**, **0.03 % of one
core** at the stream's ~820 packets/s. `test_frame_sizes.py` — 40
assertions over synthetic RTP — passes.

The 1,800-row ring would have bloated `native-stream-status`, which
several `probe_c3_*` tools poll every couple of seconds for a whole
session, so **the endpoint omits it unless `frame_series=1` is asked
for**, reporting `buckets_omitted` instead. The relay's own contract is
unchanged and the JSONL file always has every row.

### Two instrument traps, both caught before the real sessions

Each would have produced a confident wrong answer, and each is now in
`TOOLS.md`.

1. **The stream's sockets are in `/proc/net/udp6`, not `/proc/net/udp`.**
   The client's `DatagramSocket(port)` is a Java socket and binds the IPv6
   wildcard. The first sampler read `udp` alone and found the ports in
   **none of 76 rounds** — indistinguishable, read carelessly, from "the
   socket never drops".
2. **A row has thirteen fields, not the fourteen the header names**, since
   `tx_queue:rx_queue` and `tr:tm->when` are each one colon-joined token.
   A `len(parts) < 14` guard rejected **every** row of both files. `drops`
   is the **last** field, `inode` index 9. Verified against captured rows
   with a known `drops` of 17 before the sessions ran.

### The onn's receive path is not the queue

Two 20-minute sessions, 240 ten-second windows, **4,349 lost packets**:

- **the UDP socket discarded 0 datagrams** — 0 of 240 windows, video and
  audio both;
- `rx_queue` peaked at **480,512 bytes of a 2 MiB buffer** — a quarter at
  its worst, so the path is under load with headroom, not overflowing;
- below the socket, `wlan0` `rx_errors`, `rx_missed_errors`,
  `rx_over_errors`, `rx_fifo_errors` are **all +0** and device-wide UDP
  `RcvbufErrors` moved **+1** in twenty minutes.

**A larger client receive buffer is not a fix** — ruled out, not assumed,
which is worth as much here as what is ruled in.

**And one counter on the onn looks like the answer and is not.** `wlan0
rx_dropped` advances **+36,988** over a session — **16.6x** the loss — but
does not track it: per minute Spearman **0.040**, Pearson **−0.123**,
range 203-8,154 against a loss range of 0-293, with every hardware error
counter beside it at zero. It is the Android broadcast/multicast filter.
Had `p5_onn_lowlevel.py` not also read the error counters, that number
could have been mistaken for the finding.

### The reading, at the confidence it has earned

**Positively established:** the loss is not in the onn's receive path, at
the socket or below it, and it rises and falls with the count of large
frames in two independent sessions at two resolutions.

**By elimination the remaining location is the wireless hop** — the AP's

implemented; choosing is the user's decision.

| **≥ 80** | **42.5** | **45.5** | — | — | — |

**The ≥80 bucket carries 93-95 % of baseline loss at ~14x the loss/window
of anything below.** Capping deletes it **while `< 40` is not raised**.
That is the evidence that separates cause from coincidence, and it is
present in both pairs.

### Two bounds, and one arm that went the wrong way

**The benefit saturates.** A2 constrains a third harder and ties on loss
(299 vs 311). **Once the ≥80-packet population is gone there is nothing
further to win**, so the looser cap is the better setting — same benefit,
less constraint, less of the quality cost that cannot be measured here.

**VBV is a different lever, not a better one.** B1 flattened hardest of
all — every frame 14-16 packets, per-0.5 s bitrate range **6,661-7,168**
against the default's **64-15,792** — yet lost **938** against the cap's
311. The bucket table says why: **B1's `< 40` windows lose 7.79 against
the baselines' 3.33 and 4.62.** It is the only arm that made
*small-frame* windows worse. Conventional rate control **trades the tail
for a higher floor**, and by the pre-registered wording it does not show
the clean pattern.

**Nothing cost anything else.** Achieved bitrate **6,928.9-6,931.3 kbps**
across all seven (0.03 %), encoder CPU **26.6-26.9 %** median (26.1-27.5
across every arm), GPU power overlapping. A cap does not starve the
stream, it redistributes inside it.

### Drift, flagged

Baselines **2,696 / 2,189 / 2,896** — a **±15 % spread**, wider than the
~10 % the task allowed, so **drift is flagged**. It does not touch the
result: the baselines' **frame distributions are near-identical** (≥80:
718/717/734; max byte 242/245/247 KB; p50 11 packets in all three), so the
environment moved and the content did not, and **each pair clears the bar
against its own nearer bookend** (8.7x, 7.1x; 7.0x even against the most
favourable baseline for the null). Per-minute Pearson between baselines is
0.854 and 0.779; against the capped arms it collapses to 0.04-0.34, which
is the expected signature — the loss stops tracking the content once the
content's tail is gone. **Bookend every future arm.**

### What this run does not measure

**The quality cost.** No achieved QP is available on this encoder, and by
standing instruction nothing perceptual is an acceptance gate. The
stand-in is **the achieved bitrate, which does not move** — the encoder
spends the same bits; a cap changes *when* it may spend them. A 90 KB cap
is **2.7x the p90 frame and 1.5x the uncapped p99**, so it binds on ~1 %
of frames: a small number of scene changes encoded with fewer bits than
the encoder wanted. **Whether that is visible is the user's own check, and
it is the step before anything is adopted.**

### Levers, and the state the run ended in

**`-max_frame_size 90000`** is the measured recommendation.
**`-max_frame_size 60000`** is the same benefit with more constraint and a
