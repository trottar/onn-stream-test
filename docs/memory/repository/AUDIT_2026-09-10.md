## Four-player source audit

The current controller transport is more extensible than the historical “two-player POC” names imply.

Android:

- `NativeControllerSender` caps `PLAYER_COUNT` at 2.
- Controller identity maps to the first unused player slot from that count.
- Sender state is allocated from the player count.
- Each send cycle emits one **36-byte PHI1 v1 packet per player**.
- Each packet carries its own player index and a global sequence number.
- The global sequence increments for every emitted player packet.

Windows:

- `NativeControllerBridge.MAX_PLAYERS` is 2.
- It creates `MAX_PLAYERS` VX360 devices in a loop.
- It rejects packet player indexes outside that range.
- Core report/neutralization loops are mostly based on `MAX_PLAYERS`.
- Several bookkeeping structures remain literal two-element arrays: per-player updates, last-packet times, neutralized state, forced meta-button overlays.
- Status/error naming still says dual/two-player POC.
- One global receive sequence tracker matches the sender's global per-packet sequence behavior.

Implication: current evidence supports **preserving PHI1 v1 and the 36-byte packet** for the initial P3/P4 extension rather than creating a new packet format merely because player count increases. The contained production work would be count/state generalization plus diagnostics. This is not yet runtime proof.

The proven A8 launch preflight must remain: create/verify controller devices before the normal RetroArch launch. Otherwise RetroArch can initialize XInput too early and fall back.

A8 profile/editor storage currently models Player 1 and Player 2, so four-player support is not complete when four ViGEm devices merely exist. P3/P4 mapping, validation, and UI follow after slot exposure is proven.

## Security/privacy audit

The prototype correctly treats network isolation as an architectural boundary and avoids embedding user network addresses in normal diagnostics. However, the current Windows/Android implementation still carries prototype security debt: the companion control service listens broadly, Android allows cleartext traffic, Android application backup is enabled, diagnostic Activities are exported, and Moonlight remains queried for legacy compatibility. Search did not identify an obvious application-layer authorization mechanism in the audited checkpoint.

These are not instructions to redesign the current topology during four-player work. They should become explicit Phase B / remote-access security hardening items, with threat-model-driven changes and regression tests.

## Reproducibility and test audit

The repository intentionally excludes runtime binaries/state and has known clean-machine bootstrap debt around Windows-specific WGC/FFmpeg/ViGEm/process-audio pieces. This is acceptable for the current experiment but must be addressed before portability claims.

Automated CI remains thin. The project instead has many deterministic probes and hardware/runtime acceptance tests. Those probes are valuable and should become the seed for future CI where hardware independence permits, while real onn/Windows/Linux E2E tests remain separate.

## Maintainability audit

`MainActivity.kt`, `emulator_manager.py`, and `plugins/games.py` are large concentration points. Their size increases review/patch risk, especially for deterministic patching. Do not refactor them opportunistically during Phase A. After the native-only Phase B baseline is secure, targeted extraction by responsibility could reduce future patch surface.

The root `.gitignore` has repeated patterns, but current source/runtime separation is sound. Treat cleanup as low priority unless an ignore bug appears.

## Chat/process audit

The project history demonstrates that the strongest workflow is evidence-first and narrow. The most costly failures were deterministic installer/parser/quoting/state assumptions that should have been caught before delivery, and UI/source probes that tested string presence instead of user-reachable behavior.

The strongest communication pattern is explicit state classification: source-audited vs compiled vs installed vs runtime validated; and explicit terminology for controller player assignment versus physical button mapping.

## Recommended current action

Do not change production controller code from this audit. Install/commit the memory structure, then resume the four-player work with an exact **local** source audit and one targeted P1-P4 controller-slot diagnostic. A9 remains blocked on that acceptance sequence.
