## C3.L0 — Linux actuator boundary audit

Source-only audit at `310596dd0cc3ff22f3fe46e2eb025d052da90ec0`. No production
change, no new tool, no runtime execution.

### What the audit established

- Prior C3 work is Windows-era and closed through D-071, not a blank slate. It
  resumes rather than restarts.
- Bitrate has no live actuator on Linux, and the external FFmpeg CLI
  architecture (`-nostdin`, `stdin=DEVNULL`, argv-baked bitrate) forecloses one.
- Linux video is single-process (x11grab inside FFmpeg), unlike the Windows
  two-process WGC-bridge-plus-pipe topology. Windows interruption figures do not
  transfer.
- `_start_linux_locked` calls `_stop_locked()`, which also stops the FEC relay,
  so no Linux encoder-only restart seam exists.
- Resolution and FPS are Android compile-time constants, never negotiated, and
  the decoder ignores `INFO_OUTPUT_FORMAT_CHANGED`.
- FEC group size is the only in-place seam; the wire format is self-describing
  and the receiver validates 1 to 8. C4 territory.
- Pacing has no owner and no actuator.

### Negative results and gaps found

- Existing `c3_actuator_probe.py` and `c3_fixed_bitrate_probe.py` **cannot run
  on Linux**. They require `_wgc_ready()`, an HWND and `_build_ffmpeg_command`,
  and fail closed with `wgc_runtime_unavailable` before modifying anything. They
  are correct as written but not reusable without a Linux cycle implementation.
- **`_host_telemetry.start()` is never called on the Linux start path.** It is
  gated on `_capture_process is not None` inside the Windows branch, while
  `status()` still publishes a `host_telemetry` section. Sender-side host
  resource telemetry is inactive on Linux. Recorded in `docs/KNOWN_ISSUES.md`.
- **`_patches/` and `_probes/` are not covered by `.gitignore`.** The patterns
  are `privyhub_*/` and `privyhub_*_v*.zip`; the local probe directories are
  named `PrivyHub_*`, which does not match on a case-sensitive filesystem.
  Recorded in `docs/KNOWN_ISSUES.md`; confirm with `git status --short`.
- The 2026-09-18 checkpoint thinned `CURRENT.md`, `roadmap/STATUS.md`,
  `investigations/ACTIVE.md`, this dated file and `patches/PATCH_INDEX.md` to
  single lines. `PATCH_INDEX.md` lost its index of D-074 through D-139 while the
  individual patch records remained on disk.

## C3.L1 — Linux encoder-only actuator seam and continuity probe

Status: INSTALLED / DEVELOPMENT VALIDATED / RUNTIME EVIDENCE PENDING.

### What was added

`companion/diagnostics/c3_linux_actuator_probe.py`, plus a narrow platform
dispatch inside `NativeStreamManager.diagnostic_c3_actuator_continuity_cycle()`.
No new action, no new tool: the Linux cycle emits the existing probe schema, so
the existing loopback-only action and `tools/probe_c3_actuator_continuity.py`
are unchanged.

### Design decision

The Windows probe replaces capture and encoder together because raw frames
cross an inherited pipe. Linux replaces only the encoder, because x11grab is an
FFmpeg input format inside the same process. The actuator *strategy* is shared;
the implementation is not.

### Hazard found and handled during implementation

`status()` calls `_reap_locked()`, which calls `_stop_locked()` when it sees an
exited encoder. During the swap the encoder is deliberately dead, so a
concurrent `status()` would have torn down the FEC relay and session I/O — the
exact lifecycle violation the probe exists to avoid. The probe therefore clears
`manager._process` before killing the old process. A behavioural check asserts
this ordering rather than trusting the comment.

### Development validation

48 deterministic checks against a fake manager; all pass. Covers payload shape
and schema, continuity of FEC/audio/controller, the reaper ordering, absence of
any bitrate override, `_stop_locked` never being called, two failure paths, and
twelve precondition rejections each asserted to modify nothing.

Two defects were found by these checks during development and fixed before
packaging: the initial test fixture omitted the log handle a live stream always
has, and an inherited assertion from the C3.L0R1 installer still referenced the
previous patch record name.

### Not claimed

Runtime validation. The probe has not been run against a live Linux session, so
the Linux encoder-only interruption cost remains unmeasured and the automatic
bitrate controller remains blocked.

### Unchanged

`companion/plugins/games.py`, `tools/probe_c3_actuator_continuity.py`, the
Windows probe, all Android source, `.gitignore`, and every `C3.L0` audit
conclusion.

## C3.L2 — Linux actuator classification

Durable memory only. No production source change, no new tool, no probe change,
and no new runtime evidence — none was required for the classification, and none
is claimed.

### Decision

Linux is classified `video_only_restart`. `live_bitrate_reconfigure` is not
available under the current external FFmpeg CLI architecture; `unsupported` does
not apply.

Authorized: start-time profile selection before `READY`, manual and
loopback-only diagnostic changes, fallback and recovery, and `C3.L3`
characterization cycles. Not authorized: automatic adaptation during `PLAYING`,
so `C3.L4` stays blocked.

Reasons: 287-318 ms is roughly 17 frame intervals against a settled stream whose
post-cycle output gap was 5 ms; an automatic controller fires under pressure,
when a deliberate discontinuity costs most, and repeatedly rather than once; a
single accepted manual cycle is not evidence for repeated automatic ones; and
the standing preference to minimize perceptible artifacts should not be spent on
a cost that an untested lead may reduce.

This mirrors the Windows D-070 disposition, reached from Linux measurements
rather than by carrying Windows numbers across.

Record: `decisions/C3-L2_LINUX_ACTUATOR_CLASSIFICATION.md`.

### Negative results found in our own prior records

- **The recorded "immediate IDR" lead had a false premise.**
  `_build_linux_ffmpeg_command` launches a fresh FFmpeg with `-f rtp`, `-g 15`,
  `-bf 0` and no periodic-keyframe override, and `_start_linux_locked` publishes
  `bootstrap: in_band_h264_parameter_sets`. A new H.264 RTP stream begins with
  parameter sets and an IDR, so the replacement encoder's first frame is already
  a keyframe. Acting on the lead as written would have changed an encoder that
  was already doing what the change would have asked of it. The lead is
  re-registered with its premise corrected, not discarded.
- **Two headline figures were whole-session values.**
  `max_resync_to_idr_ms` and `packets_dropped_waiting_for_idr` are cumulative,
  and each session recorded two sequence resyncs against one SSRC change, so the
  session maximum may not belong to the cycle at all. `decoder_max_output_gap_ms`
  is unaffected and remains the figure to cite.
- **The terms never summed.** Spawn 115 ms plus silence 152 ms plus resync
  191 ms cannot describe a 287 ms gap; they overlap in time. That arithmetic was
  visible in the records and went unremarked.
- **The Android receiver source was not re-audited for this classification.**
  Recorded as a known gap and made the first task of `C3.L2a` rather than left
  silent.

### Next

`C3.L2a` — why is the receiver's first accepted IDR late after an encoder-only
cycle, when the replacement stream's first frame is a keyframe?

Existing instrumentation first: `logs/games/decoder_sessions/*.json`,
`logs/games/native_video_alpha.log`, the stored `C3.L1` / `C3.L1R1` payloads, and
`RtpH264Receiver.kt`. Candidates: a first IDR damaged across FEC groups at the
discontinuity (33 lost packets, 2 unrecoverable groups per session); FEC group
damage from the swap itself; receiver resync policy discarding it; encoder ramp,
largely excluded by measurement order.

Pre-registered boundary: at or below ~120 ms reopens the automatic question with
a focused gameplay observation required before acceptance; ~120-250 ms keeps the
actuator non-automatic; unchanged falsifies the lead and moves the next item to
the encoder-host architecture question.

## C3.L2a E1 — first-IDR evidence pass

Durable memory only. No production source change, no probe change, no new
runtime run. The input was the existing `C3.L1R1` session bundle from
`tools/collect_game_session_diagnostics.py`.

### The question was not answered, and that is the finding

The decoder report's slow-event list is a fixed-capacity ring:
`slow_event_retained` 128, `slow_event_capacity` 128, retaining elapsed
35,421-64,813 ms of a 64,842 ms session. `max_output_gap_ms` 287 is a cumulative
maximum whose per-event row was evicted before the report was written.

Consequence: the `C3.L1` and `C3.L1R1` runs could not have preserved the cycle's
evidence, and re-running the existing probe unchanged would lose it again. No
re-run is requested.

### What the retained window shows instead

In ordinary play with no actuator activity, `output_gap_ms` tracks `codec_ms`
one-to-one — 238/247, 200/211, 133/142, 123/131 — with `feed_delay_ms` at or
near zero, one or two frames in flight and an empty app queue. The time is
decoder time on a single frame, not transport and not IDR wait.

Session-wide: `spike_20_ms` 2,696 against 3,847 queued frames, `spike_50_ms`
285, `spike_80_ms` 80, `max_codec_ms` 297, `stale_output_drops` 184,
`low_latency_enabled` false on `c2.realtek.video.avc.decoder`.

### Consequence for C3.L2

Steady-state play in the same session reached 238 ms and 200 ms output gaps with
no actuator. The cycle's 287 ms therefore represents either ~50 ms of
attributable cost or nothing separately visible; this evidence cannot separate
the two.

`C3.L2` stands — it was deliberately conservative and withholds only automatic
in-game adaptation — but 287-318 ms must no longer be restated as "the cost of
the actuator" without that qualification, and the case for revisiting the
automatic question is stronger than `C3.L2` itself recorded.

### Also found

- `max_frames_between_idr` 27 against GOP 15: worst-case keyframe wait is
  ~450 ms, not the 250 ms the one-GOP reasoning assumed.
- The damaged-first-IDR mechanism is real in-session —
  `fec_recovered_idr_packets` 1, `fec_unrecoverable_groups` 2,
  `sequence_gap_au_drops` 4, `incomplete_au_drops` 3 — but cannot be tied to the
  cycle.
- The encoder swap is not visible in the host log's retained 500-line tail,
  which showed one continuous frame counter while the receiver recorded one SSRC
  change. Question for the probe source, not a claim that no swap occurred.
- Audio ran heavy concealment — `prolonged_starvation_events` 102,
  `concealed_underruns` 929, `stale_drops` 872 — against 7 lost packets and zero
  write errors. Outside C3; recorded because it plausibly contributes to
  perceived streaming quality.

### Next

Make the decoder session report retain the cycle: marked-window retention or a
segmented ring, `elapsed_ms` anchors for the SSRC change and sequence resyncs,
and per-event IDR context for the first accepted IDR after an SSRC change.
Diagnostic-only client work requiring a real Gradle build and its own patch.

`low_latency_enabled` false is a separate candidate with its own hypothesis. It
changes decoder configuration, which is production client behavior, and is not
authorized as part of diagnostics work.

## ANDROID-FLAT — flatten the Android source directory layout

Structural change to file locations only. No Kotlin source content was edited,
no package declaration changed, and no companion or tool source was touched.

### What moved

Every Kotlin file under `PrivyHub/app/src/main/java/com/safeiot/privyhub/`
moved up into `PrivyHub/app/src/main/java/`, keeping the `diagnostics/` and
`streaming/` subdirectories. The same was done for the two example test sources
under `app/src/androidTest/java/` and `app/src/test/java/`. The emptied
`com/safeiot/privyhub`, `com/safeiot` and `com` directories were removed.

Nineteen files, three directory levels removed each.

### Why it is safe

- every source in the app is Kotlin; the installer fails closed if it finds any
  `.java` file, because Java does require package-matching directories;
- Kotlin does not require directory/package agreement, so package declarations
  were left untouched;
- `app/build.gradle.kts` declares no custom `sourceSets`, so the default source
  roots still cover the new locations;
- `namespace` and `applicationId` are independent of directory layout, and
  `AndroidManifest.xml` names classes by fully-qualified name;
- the installer ran the real `sh ./gradlew :app:assembleDebug --no-daemon` as a
  gate and moves every file back on failure.

### Why it was done

The reversed-domain chain is inherited Java convention. For a Kotlin-only app it
bought nothing and cost three directory levels on every source file, which made
routine work on the client sources disproportionately expensive.

### Recorded

`TOOLS.md` and `MEMORY.md` now state that the layout is flat by design and that
Android Studio's "move file to package-matching directory" quick-fix must be
declined. `investigations/C3_LINUX_ACTUATOR_BOUNDARY.md` had the only live
references to the old paths and was updated; older records keep the old paths as
history.

### Unchanged

All companion and tool source, `.gitignore`, the roadmap, `CURRENT.md`,
`PHASE_C_CONTEXT.md`, every decision and evidence record, and all Kotlin file
content.
